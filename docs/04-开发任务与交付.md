## 开发组如何启动

先读业务与数据标准，明确本轮范围和取舍，再确定技术实现。技术选型未定，不进入生产编码；有前端和后端时，两边都要有结论，不能只定一边。下列编号是通用交付工作分解，不记录本项目或其他团队的完成状态，也不授予运行权限。各实现通过自己的任务表／规格关联这些交付目标，记录实际范围与证据，不在本文件维护第二份进度。当前项目的完成状态、关键路径和交接入口见[实施路线与交接](10-实施路线与交接.md)。

D01 的站点、范围、通过线和签字记录填写在[D01验证模板](14-D01验证模板.md)，不在本文件另存一份。

技术方案至少说明构建端、无AI执行端、数据输出、依赖与部署、隔离和资源回收，以及为什么比更简单方案合适。前端、后端及每个进入生产路径的层都要有选型记录；不知道哪个效果更好时，也必须按已知信息给出推荐方案、成功机会、开发效率、可维护性、可扩展性、风险和复审条件，不能开工后即兴选择。允许直接采用成熟爬虫框架和官方工具，不要求重写调度器或保留原项目结构。

## 阶段与任务

| 任务 | 输入与依赖 | 应交付什么 | 验收出口 |
| --- | --- | --- | --- |
| D01 需求映射与选型 | 本文档、获准站点与运行环境、技术栈与运行形态 ADR | 需求→设计→验证映射；前端、后端、数据、部署逐层候选权衡和推荐；成功机会、开发效率、可维护性、可扩展性、风险和复审条件；资源与开发计划，说明可后置项；按 ADR 验证框架、规则形式、存储和 Agent 适配 | 业务口径无冲突；技术选型覆盖表已建立；前、后端及进入生产路径的组件都有结论，或经批准的 Provisional 例外；未确定项有明确影响、负责人和复审条件；不允许把选择留到编码阶段 |
| D02 固定数据与导出合同 | D01、数据标准和合成示例 | 团队使用的Schema(数据结构约定)、规范化、9列业务CSV和任务报告异常索引，正价／部分描述／例外映射 | 验收场景A01～A07、A14、A18；不能仅校验格式 |
| D03 完整方案构建 | D02、实际可用工具、普通HTML站证据 | 可替换Agent从入口规划发现／获取／提取，实际试跑修订，保存完整项目或规则 | A08、A19；方案可保存，字段来源和试跑错误可定位，不依赖私有会话 |
| D04 框架独立执行 | D03方案及环境 | 无运行期LLM的实际采集入口、有效结果文件、错误／停止报告 | A08、A09、A19；结束构建会话后可运行和复跑，已知方案无逐页模型调用 |
| D05 兼容环境复用 | D04 | 方案导出／导入、依赖及环境检查；兼容Linux／WSL2执行端重跑 | A10；新任务通过当前验证后复用，不携带密钥或旧批准／进度 |
| D06 跨路径与动态获取 | D04、明确网络与浏览器能力 | 公开结构化数据、普通HTML、基础分类／分页、必要动态渲染，复用成熟工具 | A02、A03、A11、A12；同一平台不同主题不能代替跨路径证据 |
| D07 故障、隔离与数据可靠性 | 从D03起实施，D04闭环后补全恢复 | 执行权限边界、有限重试、检查点、幂等、取消回收、修复有效性 | A12、A13、A15、A20；自建资源不泄漏，停止后不再接纳迟到结果 |
| D08 任务管理与界面 | D04可信结果；D07提供相应控制；前端技术栈决策（ADR 0008） | 创建、运行、状态、暂停／恢复／取消、网址／商品查看、归档／还原、导出；构建会话 UI 后置；先补 D07 控制项 | A16、A20及界面文档；前端选型与页面范围一致；命令行可先满足核心，不把原型当真实控制 |
| D09 实站评估与发布交接 | D05～D08承诺范围 | 固定目标名单、实站执行、安装文档、版本锁定、限制、日志与验证报告 | A17；自动／辅助／失败／未完成分开，站点清单不测后删改 |

D03～D05 的方案包至少满足[采集方案与兼容契约](08-采集方案与兼容契约.md)；manifest字段不全、依赖私有会话或无法在兼容端读取，都不算完成。D07、D08 的任务状态、计数和取消语义按[任务状态与计数契约](09-任务状态与计数契约.md)。

实现前先核对[开工前检查清单](21-开工前检查清单.md)的“技术选型覆盖”：技术选型是开写前的硬门，前端和后端都要有结论；信息不足时也要给出推荐、理由和复审条件。Proposed 只能支撑实验或验证原型，不能默认进入 `app/` 生产路径；需要提前进入时登记 Provisional 例外，写明范围、负责人、回滚和复审条件。代码已合并不等于 ADR 自动 Accepted。

安全和最小权限从首次执行生成代码时就需要落实，D07不是先无约束运行、以后再补安全的许可。复杂暂停恢复和完整面板可以后置，但已提供功能要真实兑现。

## 第一阶段必须先证明什么

1. 对一个有代表性的普通HTML站，从入口得到发现、获取、提取完整方案，不要求逐URL人工配表单。
2. 结束构建Agent会话，由独立执行命令实际采集目标范围并输出合格CSV与报告。
3. 用同一方案复跑，说明是否发生模型调用、数据变化及执行成本。
4. 字段符合标准，零价／失败与部分描述透明；范围未知或预算停止明确报告。
5. 发现难点能够定位、有界处理，不以“再做更通用平台”无限推迟这一闭环。

灰度是正式执行前的质量步骤，不能把只采几个样本当成全量交付。真实网络失败时保留最小可运行交付和诊断，不伪造成功。

## 每阶段交付物

| 产物 | 最少内容 |
| --- | --- |
| 源码／方案 | 启动入口、版本、目标与适用限制、发现／获取／提取完整性 |
| 环境说明 | 支持系统、解释器／依赖／浏览器版本、安装与配置、密钥注入方式 |
| 数据与结果 | 完整有效结果文件、失败／排除／部分内容和任务结果说明 |
| 验证证据 | 实际命令、输入身份、环境、时间、预期与实测、失败和未验项 |
| 使用说明 | 怎样构建、运行、停止、复跑、导出和定位错误；承诺恢复时写实际恢复办法 |
| 维护说明 | 站点变化后的修复／复验、依赖兼容、升级与回退边界 |

不得把模型“我已完成”作为验收报告，不要求保存模型私有推理。正常公开工作说明保留事实、动作、试跑结果和下一步。

## 如何比较另一种技术实现

使用同一业务标准、固定站点及范围、相近访问环境和资源条件比较，记录总构建时间、实际模型调用、执行时间、有效商品量、部分内容比例、人工介入和维护改动。

不要只比较首次启动速度或依赖数量。某方案成功来自较小范围、更多人工确认或不同网络出口时，应分别说明；不强求相同内部架构。任何新偏好进入委托变更记录，注明哪些旧证据需要重验。
