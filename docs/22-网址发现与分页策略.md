## 用途与边界

本文回答三个问题：当前网址发现设计覆盖了什么、还缺什么；各种“下一页”机制如何分类和执行；运行时需要怎样的来源、推进、停止和证据契约。

本文是项目级设计与契约草案，不是已实现能力，也不替代[网址发现与分页（方法指导）](方法指导/02-网址发现与分页.md)的通用方法、[采集方案与兼容契约](08-采集方案与兼容契约.md)的最小 manifest 和[采集规则与任务运行时](19-采集规则与任务运行时.md)的任务账本。当前可执行子集仍以 `19` 和代码为准：`sources` 的 sitemap／listing／html_index／public_json 和 `page_param`／`next_link` 已进入 schema `1.1` 和运行时；load more、无限滚动和 POST／GraphQL 仍是目标。

**robots 统一策略（2026-11-23）**：所有阶段（分诊、构建、修复、验证、发现、执行和框架实验）都对入口同源机会式抓取一次 `robots.txt`，**只保留 `Sitemap:` 行**。404、403、429、5xx、超时或不可读都不阻塞，继续常规发现或构建；不解析 `User-agent` 组、`Disallow`、`Allow`、`Crawl-delay`，不保存全文，不把规则送进 prompt／trace／日志，不据此放行、拒绝或排除 URL。禁止直接读取完整 `robots.txt` 做分析；Sitemap URL 去重后最多保留 20 条。请求速率使用固定保守值，不因 robots 改变。robots 不是访问授权，ToS、当地法律和登录／付费／401／403 等明确拒绝仍按原规则处理；挑战页按 [ADR 0022](adr/0022-挑战页处理边界.md) 有界尝试。robots 决策记录见 [ADR 0013](adr/0013-robots只探测sitemap行.md)。

## 结论摘要

当前设计**仍不全面**，但方向是对的：P1 已补 `entry_links` + `sitemap` + `listing` 的 `page_param`／`next_link`／`load_more`／`infinite_scroll` + `html_index`（含有限深度分类递归）+ `public_json`（page／offset／cursor）；`app` 运行时已接入浏览器渲染和两种有界交互推进（静态／浏览器按 URL 类型路由、任务级进程与 profile 回收）。交互推进前先验证地址栏页码是否可直接取页，能取页就优先 `page_param`／`next_link`；内部滚动容器的追加型列表已有本地 fixture，虚拟列表已通过 hybrid adapter 接入 `app run`（本地端到端 12／12），并在 `tissus.net` 的真实 JS 渲染列表上完成 adapter discovery + 10／10 商品导出；POST／GraphQL 仍未实现。

具体差距：

- [采集方案与兼容契约](08-采集方案与兼容契约.md)要求 discovery 说明 sitemap、HTML 索引、分类／全量列表、分页和商品判型；可执行示例仍以最小来源为主，完整来源和推进见 `19`／本文。
- [采集规则与任务运行时](19-采集规则与任务运行时.md)已支持 `entry_links`、`sitemap`、`listing` 的 `page_param`／`next_link`／`load_more`／`infinite_scroll`、`html_index` 的有限深度分类递归和 `public_json` 的 page／offset／cursor；`app` 运行时已支持 `default_engine: browser` 与 `per_url_type` 的静态／浏览器路由；虚拟列表已通过 hybrid adapter 接入 `app run`（adapter 发现、声明式提取），POST／GraphQL 仍是后续。
- [方案 manifest JSON Schema](schema/manifest.schema.json)的 `1.0` 只接受旧 `strategies` 形态，`1.1` 才接受 `sources` 的 sitemap／listing／html_index／public_json 和 `advance` 的 `page_param`／`next_link`；`1.2` 增加 `load_more`／`infinite_scroll`。`fetch.browser` 现在是布尔或选项对象。
- `experiments/r06/runtime/rule.py` 的 `SUPPORTED_DISCOVERY` 仍只含旧 `entry_links`，`sources` 另行支持 sitemap／listing／html_index／public_json；`runner.py` 能处理 sitemap index／urlset／gzip、listing 的 `page_param`／`next_link`、html_index 的有限深度分类递归和 public_json 的 page／offset／cursor。`app/src/ecom_crawler/runtime/` 在此之上增加了浏览器 fetcher。
- D01 已经用过的 `sitemap_index`、`product_sitemap` 已能用 sitemap 来源表达；`public_products_json` 已能用 `public_json` 来源表达。
- 第二站 `shopthebulkstore-demo` 只把分类页第 1 页当入口；S5 分类页实际 62 个商品、每页 30，旧实现把 robots 当硬停止，所以没有验证分页；当前统一策略只保留 `Sitemap:` 行。

## 核心模型：来源、推进、判型、停止与证据

把“发现”拆成四层，避免把分页、sitemap 和入口页混成一个 `strategies` 列表：

| 层 | 回答 | 典型对象 |
| --- | --- | --- |
| 发现来源 | 候选网址从哪里来 | XML／HTML sitemap、分类树、列表页、公开 JSON、搜索、feed |
| 推进机制 | 一个列表页怎样拿到下一批 | 页码、next 链接、load more、无限滚动、offset／cursor、表单 |
| 页面判型 | 这个网址是导航、列表还是商品 | URL 形态、Product JSON-LD、价格／购买区、重复卡片 |
| 停止与证据 | 什么时候算结束、怎样证明 | 空页、无新 ID、末页、预算、部分枚举、入口贡献 |

**列表页是来源，分页是附在列表页上的推进策略。** 同一站点可以同时有 sitemap、分类树和带分页的列表；同一列表也可以先走静态页码，失败后再走浏览器滚动。把“分页”当成与 `sitemap` 平级的 strategy，会迫使一个字段同时表达来源和执行方式，后面很难扩展。

## 发现来源

| 来源 | 说明 | 典型判断 | 当前 | 目标 |
| --- | --- | --- | --- | --- |
| `entry_links` | 从入口页按选择器取链接 | 入口 HTML 已有商品／分类链接 | 支持 | 保留为最小来源 |
| `sitemap` | XML sitemap、sitemap index、`.xml.gz`；可从 robots 提取 `Sitemap:` 行 | 商品 URL 集中、可分片 | 支持：urlset／index／gzip／`Sitemap:` 行；S1 direct＋index＋robots 各 30 URL，Modellbahn gzip 30 URL | 全量／跨环境 |
| `html_index` | HTML sitemap、站点索引、页脚全量入口 | 没有 XML sitemap，但有 `/site-map`、`/all` | 支持：单页 + 有限深度分类递归；S5 `/all-products` 30 URL，Familidoo 首页 31 URL（1 层分类） | 更多站点验证 |
| `listing` | 分类、集合、搜索结果的列表页 | 一行多个商品卡片，带分页 | 支持：每个 source 一个种子 + `page_param`／`next_link`；S5 62 URL，Tognar 30 URL；MPM／Gaspard／Touchatou 两页有界验证；多个 sources 可组合 | 单 source seeds 列表、分类树 |
| `public_json` | 公开商品 JSON、目录 API、公开 feed | 列表对象已含基础字段 | 支持：GET JSON，page／offset／cursor；S4 page 30 URL，DummyJSON offset 20 URL | cursor 真实站点、POST／GraphQL、认证接口 |
| `embedded_json` | `__NEXT_DATA__`、`__NUXT__`、初始 state | HTML 空壳，首屏数据在脚本里 | 不支持 | P2 |
| `search` | 站内搜索、公开查询接口 | 只作有界补充或定点核验 | 不支持 | P3，且不作为全量目录 |

来源的优先级仍然按证据：XML sitemap／公开 feed → HTML 索引 → 分类／全量列表 → 分页 → 搜索。多入口要交叉验证，不把单一入口当全量；sitemap 条目不等于商品，仍要判型。

多种子当前用多个 `sources` 项表达，每个种子独立设置推进和预算；同一 source 内不再放 `seeds` 列表。这样规则包会长一些，但不需要在一个 source 里同时解释多个种子的推进状态。

## 推进机制

### 先判断 next 状态是否 URL 可寻址

点击“加载更多”或滚动后，页面可能不整页刷新，但地址栏通过 `history.pushState` 更新为 `?page=2`、`/page/2` 或其他稳定状态。这时先不要继续模拟交互，按下面的顺序判断：

1. 记录交互后的 URL（地址栏、`history.pushState` 或 Network 里的请求 URL）。
2. 在一个新会话或普通 HTTP 请求里直接打开该 URL，比较标题、商品数、首尾商品 ID 和正文；不要只看状态码。
3. 直接打开返回对应页 → 优先用 `page_param`、`next_link` 或 URL 模板逐页取，交互只用于第一次发现 URL 形状。
4. 直接打开回到第 1 页、返回空壳／403，或内容只在虚拟列表里逐批替换 → 才保留 `load_more`／`infinite_scroll`，并记录原因。
5. 只是 `?utm_*`、`#fragment` 或无关筛选参数的变化不算分页 URL；不要据此拼接页码。

证据至少写：交互后 URL、直接打开的状态与条目数、重复率、请求数和耗时。基准站例子：`ecolaines.com/3-laine` 使用 `kiwik infinite scroll`，但 `?page=2`／`?page=3` 可直接取页；静态 `page_param` 20／20、约 36 秒、无浏览器；同站如果只做滚动会多付浏览器成本。见 `experiments/d07/ecolaines-url/`。

2026-11-21 又对 5 个法国基准站做了同样的两请求检查：`mapetitemercerie.com` 的 `?page=2` 返回 90 个不同商品、重叠 0；`gaspardetleonie.com` 的 Shopify `rel=next` 指向 `?page=2`，24 个不同商品；`touchatou.fr` 的无限滚动配置背后是 `/page/2/`，20 + 12 个、重叠 0。规则级证据分别为主规则 10／10、`next_link` 26／26（第 2 页贡献 2）和 22／22（第 2 页贡献 2），全部静态。反例也一并记录：`atelier-leonie.fr` 单页 40 个、无 `rel=next`、`/page/2/` 为 404；`tissus.net` 静态 HTML 不含商品卡片，列表由 JS／Shopware API 加载，本轮不能判定 URL 是否可寻址。见 `experiments/d07/url-pagination-batch/`。

这一判断优先于“load more 还是滚动”的选择：**能用稳定 URL 表达下一页，就不要把点击或滚动作为常规采集路径**。

### 页面型（静态 HTTP 优先）

| 机制 | 识别信号 | 默认执行 | 终止信号 | 主要风险 |
| --- | --- | --- | --- | --- |
| 页码参数 | `?page=`、`/page/2`、`?p=`、`?paged=` | 递增或模板替换 | 空页、404、无新 ID、末页 | 参数名因平台不同；筛选／排序会重置页码；可能从 0 开始 |
| next 链接 | `<a rel=next>`、可见“Next” | 跟随 href | 无 next／disabled | `rel=next` 可能缺失；Google 已不再用它做索引信号，但抓取端仍可当线索 |
| 编号／末页 | 页码条、“Last” | 逐页，或跳到末页再回填 | 末页、无新 ID | 跳页可能漏页；页码可能动态变化 |
| 全量页 | `/all`、`view all`、单页几百条 | 一页抓完 | 页面结束 | 看起来全量，实际可能不完整；要交叉验证 |

页码参数的关键不是“把数字加一”，而是**保留列表状态**：排序、筛选、市场、语言、每页数量必须随分页请求一起保留；否则第 2 页可能变成另一个列表。页码失败不能被当作自然结束，必须记录缺口。

### 交互型（浏览器）

| 机制 | 识别信号 | 默认执行 | 终止信号 | 主要风险 |
| --- | --- | --- | --- | --- |
| load more | “Load more／Show more”按钮 | 点击；先找背后的 XHR | 按钮消失／禁用、无新 ID | 可能追加也可能替换；按钮会重渲染；需要多次点击 |
| 无限滚动 | 无分页控件，滚动后追加 | 浏览器滚动；先找 XHR | 连续 N 次无新 ID、终止文案、高度稳定 | 滚动容器可能不是 window；推荐位混入；不能只看 `scrollHeight` |
| 虚拟列表 | DOM 行数稳定，但内容在变 | 每滚一批就采集一次 | 无新 ID、到底 | 最终 DOM 不完整；必须按稳定 ID 累积，不能等滚完再抓 |
| 内部滚动容器 | `overflow:auto` 的面板 | 滚容器，不是 window | 同上 | `window.scrollTo` 对容器无效 |

**浏览器滚动怎么执行**：

- 优先找数据源。打开开发者工具的 Network，观察滚动触发的 Fetch／XHR；如果有公开 JSON、cursor 或 offset 接口，直接重放请求，比滚动稳定。
- 其次用真实输入。Playwright 里先把鼠标移到滚动容器上，再用 `mouse.wheel` 发送可信 wheel 事件；`scrollTop` 或 `window.scrollTo` 作为容器滚动和兜底。
- 等“条目数增加”或目标响应完成，不用固定 `sleep`。连续几次没有新的稳定 ID 才停。
- 虚拟列表每滚一批就抽一次，按商品 ID／SKU／canonical 累积；不能等滚到底再读最终 DOM。
- 记录滚动次数、容器、批次、最后稳定 ID、终止信号；这些和页码、cursor 一样是证据。
- 滚动是执行手段，不是发现策略。能走 sitemap、页码、next 或公开 JSON，就不要先上滚动。

`app` 运行时的浏览器 adapter 现在有两层：基础渲染按任务启动一个 Chromium/Chrome，复用一个 page，按 `wait_selector`／固定等待取渲染结果；`load_more`／`infinite_scroll` 在这一层之上做有界的点击或滚动，等条目数增加后把最终 DOM 交给现有链接发现；`infinite_scroll` 可用 `container` 滚动内部容器，本地 fixture 6／6。它仍不执行任意 JS、复杂点击序列或表单提交；虚拟列表按 ADR 0007 走 hybrid adapter（本地端到端 12／12），不在声明式层扩 primitive。

术语说明：追加式列表、替换式虚拟列表、稳定 ID 和 `rendered`／`recycled` 的区别见[开发、界面与运行时概念说明](27-开发与运行时概念行话说明.md)的“列表推进”一节；本文只保留策略和证据。

Google 的公开文档明确说爬虫不点击按钮、不触发需要用户操作的 JavaScript，所以 load more／无限滚动对 SEO 不友好；很多站仍保留 `?page=N` 或 sitemap 作为兜底，优先找这些。

### 数据型（公开 JSON／API）

| 机制 | 识别信号 | 默认执行 | 终止信号 | 主要风险 |
| --- | --- | --- | --- | --- |
| offset／limit | `offset`、`limit`、`start`、`skip` | 静态或 JSON | 空数组、`total` 到顶、`has_more=false` | 数据变动会造成重复或漏；按业务 ID 去重 |
| cursor／token | `cursor`、`after`、`page_token`、`next_cursor`、`endCursor` | 直接调公开 JSON | `has_next=false`、空／重复 cursor | token 会过期、绑定会话；崩溃恢复更难 |
| AJAX 局部 HTML | `?ajax=1`、XHR 返回 HTML 片段 | 静态重放 | 空片段、无新 ID | 需要会话／CSRF；返回的不是 JSON |
| POST／表单分页 | `form method=post`、`__VIEWSTATE` | 会话 HTTP 或浏览器 | 无新 ID、末页 | 隐藏字段／CSRF；不能简单拼 URL |
| 嵌入式 JSON | `__NEXT_DATA__`、`__NUXT__`、初始 state | 静态解析 | 数据结束 | 可能只含首屏；结构随框架变 |

公开 JSON 要先确认不需要认证、不是前端路由回退的 HTML、`total` 不是当前关键词的结果数。带请求体、复杂状态或登录态的接口，不凭猜测编一个简单 GET；用浏览器观察一次真实请求，再决定是否可复现。只有公开且允许的接口才进入默认执行路径。

### 枚举型（sitemap／分类／筛选）

| 机制 | 说明 | 终止信号 | 主要风险 |
| --- | --- | --- | --- |
| sitemap index | 子 sitemap 可能是商品、分类、图片、评论等命名子图 | 子图取完或达到预算 | 部分枚举；gzip；多市场／多门店分片 |
| 分类树 | 首页／导航／面包屑进入子分类 | 深度、预算、无新 ID | 分类重叠；同一商品多路径 |
| 筛选／facet | 颜色、尺寸、价格等筛选组合 | 预算、去重后无新 ID | 组合爆炸；不要枚举所有筛选组合 |
| 搜索 | 关键词、字母表、分类内搜索 | 结果耗尽或达到预算 | 结果有上限，不是全量目录 |

sitemap 是发现地图，不是商品清单：`<loc>` 可能混分类、政策、图片和编辑页；子图没取全时必须标“部分枚举”。筛选只用于有意的分区，不作为扩大候选的默认手段。

## 判型与去重

发现阶段先扩大候选，不按“看起来不是商品”提前删除。导航页、列表页和搜索结果即使不是商品，也可能是通向商品的路径。

- URL 形态只是假设：`/products/`、数字 ID、浅层路径、`.html` 和无扩展名都可能是商品；先抽样核对标题、Product 结构化数据、价格／购买区和主内容，再写判型规则。
- 商品正向证据：主商品标题＋价格／购买控件、Product JSON-LD、SKU／GTIN 等稳定身份。
- 列表正向证据：多个重复商品卡片、分页控件、`ItemList`、工具栏总数。
- 分类正向证据：面包屑、子分类链接、分类标题；分类页即使没有价格，也不能在发现阶段丢掉。
- 资产、购物车、结算、账户、站外链接：记录但不抓正文；遵守项目范围。

去重分两层：

- **导航去重**：按规范化 URL 去重，保留分页参数、筛选参数、排序和市场参数；去掉 `utm_*`、`gclid`、`fbclid` 等追踪参数。分页 URL 不能用商品 URL 的规则归一化，否则 `?page=2` 会被抹掉。
- **商品去重**：按业务身份去重，例如 SKU、GTIN、型号＋变体、canonical；URL 只是定位，不是身份。同一商品的多网址、多变体、多次请求只算一个商品。

`url_identity: canonical | final_url | normalized_path` 只决定导航／商品 URL 的归一口径，不替代业务键。没有 canonical 或 URL 形态不一致时，用业务键和样本核对。

## 停止条件与证据

停止原因要写进任务结果，不能只写“跑完了”：

| 停止信号 | 含义 | 证据 |
| --- | --- | --- |
| `NATURAL_END` | 没有下一页、空页、终止文案或按钮禁用 | 最后一页 URL、条目数、终止文案／控件状态 |
| `NO_NEW_ITEMS` | 连续 N 批没有新的稳定 ID | 最后稳定 ID、连续批次数、批次条目数 |
| `BUDGET_EXHAUSTED` | 达到页数／滚动次数／时间／请求预算 | 实际页数、滚动次数、请求数、剩余分支 |
| `PAGE_REPEAT` | 下一页内容与上一页相同 | 内容哈希、条目集合、URL |
| `CURSOR_REPEAT`／`CURSOR_EXPIRED` | 游标重复或失效 | 最后 cursor、响应状态、重试次数 |
| `ACCESS_DENIED`／`CHALLENGE` | 401／403、挑战页、登录／付费边界 | 状态码、最终 URL、页面标题、客户端／出口 |
| `PERMANENT_ERROR` | 404／410、内容不存在 | 状态码、URL、尝试次数 |
| `PARTIAL_ENUMERATION` | sitemap 子图或分页只取了一部分 | 已取子图数／总数、已取页数／总页数 |
| `SCOPE_EXHAUSTED` | 所有入口和分支都已处理 | 来源贡献、剩余队列为零 |

`robots.txt` 在任何阶段都不是停止信号或放行依据；每次任务最多做一次机会式探测，只保留 `Sitemap:` 行。其他行不保存、不分析，不产生 robots 排除记录，也不影响请求。探测失败只记录状态，继续常规发现。

`last_page_verified` 只有在看到自然结束信号时才为 true；因预算或失败停下时为 false，并保留剩余分支。没有可靠分母时，只报“阶段覆盖”或“入口并集”，不编造全站百分比。

发现计数至少包括：

- `navigation_pages_fetched`：实际处理的导航页数；
- `product_candidates`：判型后的商品候选数；
- `new_product_urls`／`duplicate_product_urls`：新增和重复的唯一商品 URL；
- `excluded_urls`／`failed_urls`／`pending_urls`：排除、失败、待处理；
- `new_urls_per_page`／`duplicate_rate`：入口产出率和重复率；
- `source_contributions`：每个来源的页数、新增 URL、重叠；
- `stop_signal`、`last_page_verified`、`partial_enumeration`。

这些是 `09` 现有 URL 计数的扩展；实现前先在 `09` 落定口径，不把页数写成商品数。

## 契约草案

### discovery

建议用 `sources` 表达来源，用 `advance` 表达列表页的推进方式；`entry_links` 保留为最小来源，旧规则继续可用。

```yaml
discovery:
  sources:
    - type: sitemap
      urls: ["https://shop.example/sitemap.xml"]  # 与 robots 的 Sitemap 行合并
      follow_index: true
      max_sitemaps: 20
    - type: listing
      url: "https://shop.example/collections/all"
      advance:
        type: page_param
        param: page
        start: 1
        max_pages: 20
      product_link_selector: "a.product-card"
  navigation:
    link_selector: "nav a"
    category_patterns: ['/collections/[^/]+$']
    max_depth: 2
    max_navigation: 30
  product_url_patterns: ['/products/[^/]+$']
  url_identity: canonical
  stop:
    no_new_items: 2
    max_pages: 20
    max_scrolls: 30
```

`advance.max_pages` 限制单个列表；`stop.max_pages` 是任务级总上限；两者取较小值。`page_type` 可取 `sitemap`、`category`、`listing`、`product`、`asset`、`transactional`、`external`；`source` 取本文“发现来源”表中的类型。所有 sitemap 来源都会并入本次 robots 探测到的 `Sitemap:` URL；`sitemap.robots` 保留兼容但忽略。

### advance

| 类型 | 最少字段 | 执行层 | 说明 |
| --- | --- | --- | --- |
| `none` | — | 静态 | 单页全量，不推进 |
| `page_param` | `param` 或 `url_template`、`start`、`max_pages` | 静态 | 保留排序／筛选／市场状态 |
| `next_link` | `selector` 或 `rel`、`max_pages` | 静态 | 跟随 href，不假设参数名 |
| `load_more` | `button_selector`、`max_clicks` | 浏览器 | 点击后等条目数增加；按钮重渲染要重新定位 |
| `infinite_scroll` | `container`、`mode`、`max_scrolls`、`settle_ms`、`no_new_stop` | 浏览器 | `mode` 可取 `wheel`／`scroll`／`auto` |
| `offset_api` | `endpoint`、`offset_param`、`limit_param`、`items_path`、`total_path` | 静态／JSON | 空数组或 offset ≥ total 停止 |
| `cursor_api` | `endpoint`、`cursor_param`、`items_path`、`next_cursor_path`、`has_next_path` | 静态／JSON | cursor 不透明，不自行拼接 |
| `form_post` | `form_selector`、`submit_selector`、`max_pages` | 会话 HTTP／浏览器 | 保留隐藏字段、CSRF 和会话 |

`page_param` 已在 S5 跑通 62 URL；`next_link` 已在 Tognar 跑通 30 URL（选择器 `link[rel=next]`）；`public_json` 的 page 在 S4 跑通，offset 在 DummyJSON 公开 API 冒烟，cursor 仍由 fixture 覆盖。`load_more` 和 `infinite_scroll` 已在 `app` 的浏览器 adapter 上跑通本地 fixture 和 `scrapingcourse.com` 公开练习页（各 15／15 商品，约 84／88 秒）；声明式层只支持追加型列表，虚拟列表已通过 hybrid adapter 接入 `app run`（本地端到端 12／12；`tissus.net` 真实 JS 渲染列表 10／10），`form_post` 仍是设计目标。

### 版本与校验

- `schema_version: "1.0"` 只接受 `strategies: ["entry_links"]`；`1.1` 已加入 `sources` 的 sitemap／listing／html_index／public_json 和 `advance` 的 `page_param`／`next_link`；`1.2` 增加浏览器型 `advance`（`load_more`／`infinite_scroll`）；`1.3` 增加可选的 Shopify `product_source`。旧执行端遇到不认识的版本直接拒绝；新规则默认用 `1.1`，需要浏览器推进时用 `1.2`，需要 `/products.json` 产品源时用 `1.3`。
- `sources` 存在时，`strategies` 必须省略或仅为 `["entry_links"]`，避免两套来源同时生效。
- `load_more`／`infinite_scroll` 要求导航引擎为 `browser`，并使用 `schema_version: "1.2"` 或 `"1.3"`。`1.3` 可同时声明 Shopify 商品 JSON 来源。其他发现字段的校验见[运行时能力清单](19-采集规则与任务运行时.md#规则引擎能力清单)。
- 浏览器能力不是默认值。`fetch.default_engine: static` 时，规则包声明滚动或点击应被拒绝，而不是静默降级。
- `fetch.robots` 不再作为门禁，旧值只作兼容读取，运行时忽略。所有 sitemap 来源都会自动并入机会式探测到的 `Sitemap:` URL；不解析规则、不保存全文。
- 当前 `rule validate` 尚未调用 JSON Schema；在 P1 前补上，避免文档、schema 和运行时三套语义。

### 运行时导航项

现有 `navigation` 工作项是正确雏形，缺的是让它产出新的 navigation 工作项，并保存推进状态。

建议字段：

```json
{
  "item_type": "navigation",
  "url": "https://shop.example/collections/all?page=2",
  "page_type": "listing",
  "depth": 1,
  "parent_url": "https://shop.example/collections/all",
  "source": "listing",
  "advance": {"type": "page_param", "param": "page"},
  "advance_state": {"page": 2, "last_item_key": "sku-123", "content_hash": "..."},
  "listing_state": {"sort": "default", "filters": {}, "market": "US", "page_size": 30},
  "attempts": 1
}
```

- `depth` 只在实际换层时增加（分类→子分类、sitemap→子图）；同一列表的页码推进不增加 `depth`，否则会被 `max_depth` 提前截断。
- `advance_state` 是断点：页码模式存下一页页码；offset 模式存 offset；cursor 模式存最后 cursor；滚动模式存滚动次数和最后稳定 ID。
- `listing_state` 保存排序、筛选、市场、语言和每页数量；这些变化会改变列表成员，不能丢。
- 导航项处理完先写结果和检查点，再标记完成；不能先标记完成、后补结果。
- 滚动模式的恢复最弱：能回到最后稳定 ID 就续，不能就重开种子并去重；在结果里写清重放范围。

### 执行层级

| 层级 | 能力 | 典型场景 | 默认 |
| --- | --- | --- | --- |
| T0 静态 HTML | 请求、解析链接／sitemap | 静态列表、页码、next | 首选 |
| T1 公开 JSON | 静态请求、解析 JSON | offset／cursor、嵌入式 JSON | 次选 |
| T2 浏览器渲染 | 渲染后读 DOM，不交互 | JS 渲染列表、空壳页 | 必要时 |
| T3 浏览器交互 | 点击、滚动、会话 | load more、无限滚动、虚拟列表 | 有界使用；v0 已实现追加型 load_more／infinite_scroll，虚拟列表另有已接入 `app run` 的 hybrid adapter |
| T4 人工／辅助 | 登录、付费、年龄门、地区限制、站点明确拒绝 | 访问控制边界 | 停止，不自动绕过 |

选路顺序是“最便宜的足够方案”：sitemap／HTML 索引／页码／next／公开 JSON 优先；T2 只在原始 HTML 没有内容时；T3 只在交互确实产生新数据时；T4 不进入默认路径。

规则层和执行层的边界见[规则层与爬虫框架边界 ADR](adr/0007-规则层与爬虫框架边界.md)：C1 最多保留 `load_more`／`infinite_scroll` 两个 primitive，虚拟列表、网络捕获、多步会话等 C2 能力走 `hybrid` adapter，不继续扩 DSL。

- sitemap：urlset、sitemap index、`.xml.gz`、混合分类／商品、子图上限。

### 浏览器滚动

- 已用本地 fixture 和 `scrapingcourse.com` 公开练习页做无验收性质的技术冒烟；不把结果写成业务站点验收。
- 已检查：load more 点击、window 滚动、内部容器滚动（`container`，本地 fixture 6／6）、连续无新 ID 停止、资源回收；虚拟列表逐批采集已通过 hybrid adapter 接入 `app run`（本地端到端 12／12）；真实站点替换式虚拟列表按低优先级处理，暂不主动检查；更复杂的内部滚动仍待检查。
- 通过标准是“批次、稳定 ID、停止信号、请求数可复核”，不是“页面看起来到底了”。

## 风险与不做

- 不做通用全站蜘蛛；只做有界、可审计的来源和前沿。
- 不枚举所有筛选／排序组合；需要分区时先定业务边界。
- 不无上限滚动；必须有 `max_scrolls`、`no_new_stop` 和时间／请求预算。
- 不用 `scrollHeight` 或“加载动画消失”证明到底；以稳定 ID 和终止信号为准。
- 不把虚拟列表的最终 DOM 当完整数据；必须逐批累积。
- 不把私有 XHR、登录接口或未公开 API 当公开数据源；需要认证就停。
- 不绕过登录、付费、401／403 等明确拒绝、年龄门或地区限制；挑战页和验证码按 [ADR 0022](adr/0022-挑战页处理边界.md) 尝试，仍被拒绝就停止；只探测 robots 的 Sitemap 行不等于访问控制取消。
- 不把“只探测 robots 的 Sitemap 行”写成法律许可或生产合规结论；对外分发仍按 `17`／`21` 走 go／no-go。
- 不保存整页 HTML；只保留 URL、计数、字段和必要的有界样本。

## 开放问题

- `schema_version` 用 `1.1` 增量，还是直接 `2.0` 重排 `discovery`？建议 `1.1`，旧 `entry_links` 继续可用。
- sitemap 来源是否默认探测 robots 的 `Sitemap:` 行？已定：所有阶段机会式探测一次，sitemap 来源自动并入，不再由 `robots: true` 控制。
- 浏览器滚动是否进入 v1？本文建议 P3，不阻塞 P1 的静态发现。
- S5 的 `?p=2` 实际响应是否稳定？需要在 P1 中做一次有界验证；若被挑战或 403，记录边界，不换出口。
- 是否需要第三个允许分页的站点做正向对照？如果 S5 的实际响应不具代表性，需要补一个。
