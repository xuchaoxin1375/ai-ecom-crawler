## 站点、批次、规则包与任务

**一句话**：站点是采集目标，批次是一组站点，规则包是某个站点的采集方案版本，任务是一次执行。

**通俗解释**：像装修。站点是要装修的房子，批次是一个小区的装修项目，规则包是某套房子的施工图，任务是一次施工。用户会说“这个小区这 20 套房子要装修”，不会先说“把 20 张施工图拿给我选”。施工图重要，但它是内部资产，不是用户入口。

**准确解释**：

| 对象 | 是什么 | 关系 |
| --- | --- | --- |
| 站点 | 一个采集目标网站 | 可以有多个规则包版本和多个任务 |
| 批次（项目） | 一次提交或交付的一组站点和任务 | 包含多个站点；汇总由成员任务派生，不是任务状态或计数单位 |
| 规则包 | 某个站点的一套可执行采集方案版本 | 一个站点可以有 0～N 个；任务绑定其中一个版本 |
| 任务 | 一个站点 × 一个规则包版本 × 一个市场的一次执行 | 一个站点可以有多个任务；结果属于任务 |

**常见误解**：

- 规则包不是站点。一个站点可以有多个规则包版本，也可能暂时没有规则包。
- 规则包不是任务。规则包可被多个任务复用；任务有状态、计数和结果，规则包没有。
- 批次不是任务状态或计数单位。批次用于组织、筛选和交付，状态由成员任务派生，不把商品数简单相加。
- 任务控制台技术视图仍保留“规则包下拉框”；批次主流程已从站点／批次开始，规则包在站点背后匹配，不再作为业务入口。

**本项目现状**：批次工作台阶段 1 已进入 v1 并完成真实批次验收：批次列表、导入匹配、批次详情、部分启动、批次级暂停／取消、汇总和导出已可用；任务控制台并入同一 Vue 外壳的 `/tasks` 技术视图。仍未实现的是自动构建、完整多轮构建会话、批次级配额、整批合并 CSV 和更大规模真实批次验收。目标工作流、对象模型和线框见[用户工作流与前端信息架构](33-用户工作流与前端信息架构.md)。

## 开发切片

**一句话**：把开发拆成若干“能独立跑通、能独立验收”的小闭环，做完一个再扩展下一个。

**通俗解释**：像装修先打通一间样板间——水电、墙面、家具都能用，再复制到其他房间；不是先买齐所有材料，也不是只刷一面墙。

**准确解释**：开发切片是一个范围受控、纵向贯通、可独立运行和验收的增量。纵向贯通指它穿过完成这件事所需的各个层次，从输入一直做到可观察的结果；它可以很小，但要真实可用，并带上必要的测试、证据和说明。多数切片是端到端的纵向闭环，也可以按测试或交付边界划出一小段，但边界必须写清。

**常见误解**：

- 不是数据分片或分库分表。本项目说“两站切片”，指的是用两个站验证同一条规则或运行时路径，不是把两个站的数据切成两份。
- 不是只做一层。只做页面、只做接口或只做数据库迁移，通常只是任务分解；除非明确说明它是某个完整切片的前置。
- 不是页面或功能模块。一个切片可以跨多个页面和层次；一个页面也可能分属多个切片。整体设计基线按用户旅程组织，不按切片拆分。
- 不是占位页面和假数据。切片可以小，但要能真实运行、能被验收。
- 不是一次性大版本。切片的意义是逐步加宽，每步都能停下来检查。

**本项目现状**：

- [D08 任务服务与界面设计](26-D08任务服务与界面设计.md)的“实施切片”把界面工作拆成：服务骨架与只读 API → 规则与创建 → D07 控制项 → 归档与完整导出 → 验收收口。
- 其中“只读 Web 切片”是第一个可运行闭环：先提供健康检查、任务列表／详情、URL／商品分页和导出，不启动 worker，也不含创建和控制。当前 `serve` 已在此之上接入创建、控制、SSE、归档和默认托管 worker；设计评审已于 2026-11-22 通过，A16 1280 已于 2026-11-23 验收；跨浏览器／读屏未测。
- [采集规则与任务运行时](19-采集规则与任务运行时.md)的“最小运行时切片”先跑通 discovery／product 两个任务、SQLite 账本和并行控制；“两站切片”是在第二个站只加规则包，验证复用。
- “两站切片”和“最小切片”描述的是验证范围，不是正式生产范围；文档会同时写清未覆盖项。

**负责人可以追问**：

- 这个切片的输入、输出和验收证据是什么？
- 这个切片的用户任务边界是什么？它跨哪些页面，哪些页面留给后续切片？
- 它明确不做什么？哪些留给下一个切片？
- 能否单独演示，而不依赖后一个切片才能跑？
- 测试和文档是否随切片一起交付？

## 界面设计：线框、视觉稿与原型

**一句话**：线框回答“页面上有什么、先看什么、怎么走”；视觉稿回答“长什么样”；原型回答“点起来顺不顺”。

| 产物 | 回答的问题 | 不回答什么 |
| --- | --- | --- |
| 线框（wireframe） | 页面分区、信息层级、入口出口、主次操作和关键状态 | 颜色、字体、图标风格和精确间距 |
| 视觉稿（mockup） | 颜色、字体、图标、间距和整体风格 | 用户任务是否成立、状态是否齐全 |
| 原型（prototype） | 点击后的流程、交互反馈和状态转换 | 真实数据、接口契约和最终实现质量 |

**原型的范围**：原型可以是低保真（可点击线框或简单交互）或高保真（带视觉和接近真实的交互），重点是验证流程、交互和状态，不要求真实后端数据，也不等于最终实现。项目文档里的“原型”有时也指技术原型（如 R06／R16 的最小可运行实现），那是验证技术可行性，不是界面原型；阅读时看上下文区分。

**线框的准确解释**：线框是低保真的页面结构表达。它用区块、文字和占位符标出页面有哪些区域、每块装什么、哪些信息优先、从哪进到哪去，以及空、加载、失败等状态怎么呈现。线框可以是 ASCII、灰度框图或简单 HTML；形式不重要，能否支撑评审和分工才重要。它不是视觉稿，也不是可点击原型。

**信息层级**：首屏先回答什么问题，哪些信息折叠或放到二级页。它不是 API 字段清单；API 有的字段不一定首屏展示。

**状态矩阵**：逐项列出加载中、空、读取失败、数据过时、部分结果、禁用、已受理、已完成等状态，以及用户在每个状态下的下一步。它不是只画正常路径，也不是任务状态表的替代品。

**设计门**：新增或改版页面前，先完成页面清单、关键流程、信息层级与线框、状态矩阵和取舍说明并评审的关口。它挡的是“没想清楚就写页面”，不是挡实现进度，也不是最终验收。

## 线框确认与验收的区别

**一句话**：在写页面前，由需求负责人按真实任务确认页面结构、信息优先级、关键流程、状态和取舍，而不是确认颜色。

**通俗解释**：像装修前确认平面图和动线，不是确认墙漆颜色。平面图确认后再施工，改结构的代价最低。

**准确解释**：线框确认是设计门中的一个决策点。负责人要判断：目标用户和任务对不对；首屏先回答什么问题；入口和出口是否走得通；主操作是否超过三个；加载、空、失败、部分结果和禁用状态是否有出口；哪些字段只是 API 有、用户其实不需要；这次明确不做什么。确认结果应是接受、修改后接受或拒绝，并留下评审记录和待办。它不是让负责人自己画线框，也不是对最终视觉签字。

**常见误解**：

- 不是视觉确认。颜色、字体、图标和间距可以后定；结构错了再改，代价更大。
- 不是最终验收。后面还有视觉、响应式、无障碍、真实数据和实机验收。
- 不是技术评审。技术预览、接口联调、测试全绿和截图只证明部分事实，不能替代业务确认。
- 不是“页面已经写出来了，所以设计默认成立”。实现不能反推设计合理；应先确认设计稿，再映射到实现。
- 不是让业务方画图或写 CSS。Agent 先给可预览的结构、状态和取舍，业务方只判断任务和选择。
- 不是所有细节一次冻结。确认的是方向和结构；后续可以改，但结构级改动越晚越贵。

**本项目现状**：

- [D08 前端设计包与评审](28-D08前端设计包.md)把“信息层级与线框”列为最小设计包的必选产物，并规定新增或改版页面前先评审；技术预览、接口联调页和按 API 字段直排不算设计评审。
- [D08 初步设计稿](29-D08初步设计稿.md)给出任务列表、创建、详情和空／失败／归档状态的 1280 线框、设计取舍和已确认项；2026-11-22 通过项目方设计评审，A16 1280 已于 2026-11-23 验收。
- 1280×900 技术复核只证明页面能打开、无横向溢出等事实，不等于项目方确认；A16 需要设计稿评审、实现证据和项目方确认，三者已于 2026-11-23 齐备。
- 窄屏完整矩阵、深色主题和完整响应式按交付前适配阶段处理，不在开发期逐切片作为门禁。

**负责人可以追问**：

- 这次要我确认的是哪些页面、哪些流程和哪些状态？
- 首屏先回答什么问题？哪些字段只是 API 有、用户不需要？
- 主操作有几个？危险操作放在哪里？空、失败、部分结果时用户下一步是什么？
- 哪些是本次明确不做？确认后会落到哪些实现切片？
- 技术预览或截图是否已经被误当成确认？谁记录确认结果？

**线框确认**不是严格统一的行业术语；英文常写 `wireframe review` 或 `wireframe sign-off`，本项目用它指 D08 设计门中的业务确认动作。

## 租约

**一句话**：给 worker 一张限时“工作证”，证明它在一段时间内独占某个任务或工作项；到期或失联就作废，别人可以接手。

**通俗解释**：像图书馆借书。借期内书归你使用；超期不还，管理员可以收回再借给别人。借书条不是永久所有权，也不是“这本书永远归我”。

**准确解释**：租约（lease）是一种带有效期和续约机制的独占持有权。持有者要定期续期，通常通过心跳表示自己还活着；租约到期后，其他 worker 可以重新获取。为防止“过期后原持有者又醒过来继续写”，还需要归属校验或版本号（常叫 fencing token），并在账本里用原子条件更新拒绝旧持有者的写入。它解决的是多进程或多 worker 下“这一项现在归谁处理、崩溃后由谁接手”的问题。

**为什么需要**：

- 启动时对账只能处理“我知道自己重启了”的情况；如果两个 worker 同时活着，都可能把别人的 `RUNNING` 当成孤儿任务重排，造成重复处理。
- 租约让同一时刻只有一个合法持有者，并让接管有明确的时间边界和写入边界。
- 浏览器、独立进程或未来多机执行时，单实例锁不够用，租约是常见的下一步。

**常见误解**：

- 不是普通互斥锁。锁通常要显式释放，进程崩溃后可能留下未释放的锁或锁文件；租约会过期，允许接管。
- 不是任务状态。`RUNNING`、`PAUSED` 是任务生命周期；租约是“谁在跑”的运行时凭据，可能单独存储。
- 不是队列。队列决定“下一个做什么”，租约决定“这一项现在归谁”。
- 不是法律意义上的租约，也不是永久所有权。
- 不是“加个锁”就完成了。没有过期、续约和旧持有者拒写，仍然可能出现两个 worker 同时写。

**本项目现状**：

- v1 默认仍是单进程 + 线程池 + 单实例锁；单实例锁保证同一账本只有一个 worker 进程，启动和周期性对账处理崩溃遗留。
- `app` 已实现单机跨进程租约：任务领取、`lease_token`、心跳续约、过期回收和旧持有者拒写均有 T1／T2 测试；`worker`／`serve` 加 `--allow-multi-worker` 时跳过单实例锁，由租约协调多个进程。
- 跨机租约为 v1 外，未验证；租约存放在本机 SQLite，不能直接代表多机共享账本。需要多机时另立共享账本／队列阶段。
- 浏览器 adapter、进程／目录登记、任务级 profile、单进程 `--max-browser-tasks` 槽位和 SQLite `browser_slot` 跨进程协调已落地；hybrid adapter 默认临时 context，`profile_mode=task` 才创建任务级 profile；跨机浏览器配额为 v1 外。

**负责人可以追问**：

- 近期是否真的需要多进程或多机？如果暂时不需要，单实例锁加上启动对账可以支撑当前阶段。
- 如果要做，租约设计是否写清有效期、续约、过期回收、旧持有者拒写和崩溃接管测试？
- 不要把“已经加了锁”当成“已经支持多 worker”。

## worker、进程、线程和线程池

| 词 | 通俗解释 | 准确解释 | 不要混淆 |
| --- | --- | --- | --- |
| worker（执行器） | 真正干活的执行单元 | 从任务账本领取任务或工作项并执行的进程或线程 | 不是任务本身；一个 worker 可以处理很多任务 |
| 进程 | 一个独立运行的程序实例 | 有独立内存和资源；一个进程崩溃通常不直接影响其他进程 | 不是线程；跨进程协调和通信成本更高 |
| 线程 | 进程内的一条执行流 | 共享进程内存；创建和切换较轻，但一个线程出错可能影响同进程 | 不是独立进程；不能靠线程实现跨进程接管 |
| 线程亲和 | 某些对象只认创建它的线程 | 库或对象绑定创建线程，跨线程调用会报错或行为不稳定 | 不是线程安全；也不是把线程绑定到某个 CPU 核 |
| 线程池 | 一组可复用的线程 | 用固定数量的线程控制并发度，避免频繁创建销毁 | 不是多进程，也不等于多机或分布式 |
| 进程池 | 一组可复用的进程 | 用多个进程承载任务，进程间有独立内存和崩溃边界 | 不是线程池；进程启动和通信成本更高 |
| worker 池 | 一组 worker 执行单元的集合 | v2 语境下通常是多个任务进程；任务分配给其中一个执行 | 不是线程池，也不是任务队列 |

**本项目现状**：

- [ADR 0003](adr/0003-任务运行时与并行模型.md)的 v1 目标是单进程 + 线程池 + SQLite WAL，目标 2 个任务并行、每任务 2 个 product worker；当前 CLI／`serve` 默认 1，A20 同进程已通过。v2 才考虑每任务进程或 worker 池。
- 当前 `app` 默认仍是单 worker；`run` 固定 `max_tasks=1`，`serve` 默认托管一个 worker，`--no-worker` 可关闭。加 `--allow-multi-worker` 后可让多个 worker 进程共享同一账本，每个进程仍按自己的 `max_tasks` 限制并发。
- 文档里的 `Worker` 有时指代码里的类或线程，有时指 `ecom-crawler worker` 这个进程命令；看上下文区分，不要把它当成任务。

**常见误解**：

- “线程池”不等于“多进程”。线程共享同一个进程，崩溃隔离和跨机接管能力都有限。
- “worker 多”不等于“任务多”。worker 是执行者，任务是有生命周期和计数的采集实例。
- “开了多个线程”不等于“支持多 worker 同时消费同一账本”；后者需要锁或租约。

## v2：每任务进程、worker 池与故障隔离

**一句话**：v2 把采集任务从“主服务里的线程”推进到“每任务进程或 worker 池”，用进程边界隔离浏览器、adapter 和单个站点的崩溃；任务、规则和结果契约不变。

**通俗解释**：v1 像所有工人在同一个车间干活，一个人触电或把车间堆满，其他人也受影响；v2 像给任务分独立工位，工位起火只关这一间，其他任务继续。

**准确解释**：

- **每任务进程**：一个采集任务在独立 OS 进程中运行，任务结束、取消、租约过期或崩溃时回收该进程及其子进程和临时目录。它不是“每任务一个线程”，也不是“每个请求一个进程”。
- **线程亲和**：某些库（如 Playwright 同步 API）的对象只能在创建它的线程使用，跨线程调用会报错或行为不稳定；v2 用独立进程隔离这类生命周期，而不是把浏览器对象在线程池里传来传去。
- **worker 池**：一组可复用的 worker 执行单元。v2 语境下通常是多个任务进程；任务分配给其中一个执行。它既不是线程池，也不是任务队列：队列决定“下一个做什么”，池决定“谁来执行”。
- **故障隔离**：把单个任务／站点的崩溃、内存泄漏或浏览器挂起限制在局部，不拖垮主服务和其他任务。它不是自动重试，不是业务容错，也不是安全沙箱。
- **子进程与进程组**：adapter、浏览器、harness 等由主服务或任务进程启动的独立进程；超时或取消按进程组终止（Windows `taskkill /T`，POSIX `killpg`），避免留下孤儿。
- **浏览器实例与资源配额**：浏览器实例是一个运行中的 Chromium／Chrome 进程及其 profile（持久化目录）／context（隔离的会话容器），是配额单位；资源配额还包括任务数、内存和请求上限。配额不足时排队或等待，不是任务计数。
- **IPC**：进程间通信，用于传任务上下文（任务 ID、规则版本、范围、预算、输出目录等）、事件、结果和取消信号；不是 HTTP API，也不是任务账本。

**本项目现状**：

- v1 仍是单进程 + 线程池 + SQLite WAL；`Worker` 用线程执行任务，浏览器任务受线程亲和和进程内崩溃影响。
- v2 未实现。当前代码里的“子进程”主要用于 adapter、浏览器和构建 harness，不等于 v2 的每任务进程。
- v2 的具体形态（严格每任务一个进程，还是任务分配给 worker 池）在实现时确定；共同点是把执行从主服务线程移到独立进程边界。
- v2 不改变任务状态、计数、规则包和结果契约；进程隔离不是安全沙箱，安全沙箱仍按 ADR 0006 另行评估。

**常见误解**：

- “v2 是为了让更多站点同时跑”：不是。v2 首先是隔离和稳定性，吞吐是附带收益；更多站点仍受任务槽位、浏览器配额和站点限速约束。
- “每任务进程 = 每任务线程”：不是。线程共享内存，进程有独立地址空间和崩溃边界。
- “worker 池 = 线程池”：不是。线程池在单进程内复用线程；worker 池在 v2 语境下是多个进程。
- “故障隔离 = 自动重试”：不是。隔离只限制影响面，重试和恢复仍按任务／工作项契约。
- “子进程 = 安全沙箱”：不是。进程边界不是权限边界，不能替代文件、网络和密钥隔离。
- “浏览器实例 = 浏览器 profile”：不是。实例是运行中的进程，profile 是持久化目录／上下文。

**负责人可以追问**：

- v2 选每任务一个进程，还是 worker 池？进程启动成本和任务规模是否匹配？
- 任务进程如何传上下文、事件、结果和取消信号？IPC 协议和超时如何验证？
- 进程、浏览器、profile 和临时目录由谁登记、由谁回收？崩溃接管后如何避免旧进程继续写？
- 进程隔离能限制哪些故障？哪些仍需安全沙箱、权限或网络策略？

## 并行、并发与批次启动

**一句话**：并行是多个任务或工作项在同一时间实际执行；批次启动只是把多个站点任务放进队列，不等于同时运行。

**通俗解释**：像餐厅同时开几张桌。`max_tasks` 是同时开桌的数量；批次启动是把一批客人排进等位名单，名单再长，也要看现在有几张空桌。`max_browser_tasks` 则是其中需要包间的客人数量上限。

**准确解释**：

- 任务级并行：多个采集任务同时处于 `RUNNING`；由 worker 的 `max_tasks`（CLI `--max-tasks`）控制。当前 `run` 固定 1，`worker`／`serve` 默认 1。
- 工作项级并行：单个任务内多个 navigation／product 工作项同时处理；由规则或任务里的 `concurrency.navigation`／`product` 控制。
- 浏览器槽位：browser／hybrid 任务还受 `max_browser_tasks` 限制；同一账本上的多个 worker 通过 SQLite `browser_slot` 协调。
- 站点限速：同一 worker 进程内按域名共享限速器；不同 worker 进程各自有限速器，`--allow-multi-worker` 时同一域名的总速率可能叠加。
- 批次启动：`POST /api/batches/{id}/start` 为每个可采站点创建一个任务并置为 `QUEUED`；返回受理和跳过原因，不改变 worker 槽位。

**本项目现状**：

- v1 运行时已具备任务级并行能力；A20 同进程已通过（两个任务、至少一个同域、暂停／取消隔离），跨进程 A20 资源配额和批次级配额仍未闭合。
- 默认 `max_tasks=1`：批次里 3 个可采站点会按队列逐个执行；显式 `--max-tasks 3` 才会尝试同时运行 3 个任务。3 个及以上任务没有单独验收，不写成 v1 承诺。
- browser／hybrid 任务还受 `max_browser_tasks` 限制；当前实现先领取任务再等待浏览器槽位，任务可能已显示 `RUNNING` 但尚未实际抓取，不能只看状态判断是否在跑。
- 版本归属：v1 是单进程 + 线程池的任务级并行；v2 是每任务进程／worker 池，服务浏览器、adapter 和故障隔离；v3 是外部队列 + 多 worker，面向多机、大量任务和远程执行。3 个静态站点不需要等 v2；但稳定多站并行、浏览器隔离和批次级配额属于 v2／后续阶段。

**常见误解**：

- “批次启动 14 个站点”不等于 14 个任务同时运行；先看 worker 的 `max_tasks` 和 `max_browser_tasks`。
- “任务已创建／已入队”不等于“正在执行”；`QUEUED` 是等待，不是失败。
- “任务槽位”不是站点数、队列长度或浏览器实例数；三层上限要分开看。
- “规则已写好”不等于“站点可采”；站点还需要规则包可用、状态为 `ready`，批次启动才会为它建任务。
- “多开几个 worker”不等于自动安全地提高并发；同一域名的限速、浏览器槽位和 SQLite 写入都要一起考虑。

**负责人可以追问**：

- 要同时跑几个站点？它们是静态页还是 browser／hybrid？后者受浏览器槽位限制。
- 这些站点是否同域？同域时总速率是否仍符合站点礼貌和 `per-domain-rps`？
- 目标是“排队后逐个跑完”，还是“必须同时跑”？前者默认 1 就够，后者要显式配置并补验收证据。
- 是否需要批次级配额、故障隔离或跨机执行？需要时按 v2／v3 评估，不把 `--max-tasks` 调大当成完整方案。

## 浏览器 adapter 与资源回收

**一句话**：浏览器 adapter 把“这个网址的渲染后 HTML 是什么”变成和静态 fetcher 一样的取数接口；它不是会自己点击、滚动或过验证码的机器人。

**准确解释**：浏览器 adapter 通常按任务启动一个 Chromium／Chrome，准备独立 profile，打开页面，等目标 DOM 出现，读取渲染后的 HTML，再交给同一个提取层。它需要和静态 fetcher 共享限速、重试和任务账本，但浏览器有自己的生命周期：进程、profile 目录、页面、CDP 连接都要在任务结束、取消或崩溃接管时回收。Playwright 的同步 API 还绑定创建它的线程，所以浏览器任务不能把 item 随便丢进线程池。

本项目的做法：

- `fetch.default_engine` 决定默认引擎，`per_url_type` 按 `navigation`／`product` 路由；静态和浏览器可以混用。
- 浏览器按任务懒启动，一个浏览器 + 一个 page 串行复用；进程 PID 和 profile 路径写入 `task_resources`，带租约令牌。
- 先等 `wait_selector` 等就绪信号，再读渲染后的最终状态；挑战壳的 503 不等于最终页面失败，但也不等于可以绕过访问控制。
- 正常结束、取消和租约过期接管都会回收；本机强杀 worker 的演练见 `experiments/d07/browser-mercerine/`。

常见误解：

- “能渲染”不等于“能处理虚拟列表或任意点击”。有界 `load_more`／`infinite_scroll` 是单独的动作层；虚拟列表逐批采集走 hybrid adapter（已接入 `app run`；真实站点替换式列表未验证），任意点击序列和表单提交仍未实现。
- “浏览器能打开”不等于“站点可全量采集”。样本、预算、出口和长期稳定性仍要单独记录。
- “一个任务一个浏览器”不等于“每个请求一个浏览器”；也不是“所有任务共享一个浏览器 profile”。

当前 `app` 的浏览器 adapter 已覆盖渲染、静态／浏览器路由、任务级回收和有界 `load_more`／`infinite_scroll`（含内部容器追加型）；虚拟列表按 ADR 0007 有 hybrid adapter 并已接入 `app run`（本地端到端 12／12；真实站点替换式列表未验证，低优先级），更复杂的内部滚动仍未实现；跨机回收为 v1 外；hybrid adapter 默认临时 context（不建 profile），`profile_mode=task` 才登记并清理；单进程／跨进程 browser 槽位已补。参考：[采集规则与任务运行时](19-采集规则与任务运行时.md)、[测试策略](23-测试策略.md)。

## 列表推进：追加式与替换式虚拟列表

**一句话**：列表页往下加载时，有的站点把新条目接在后面，有的站点只保留当前屏幕附近的几行并把旧行换掉；后者就是虚拟列表，必须边滚边记，不能等滚到底再读。

**通俗解释**：把列表想成一张桌子。追加式列表像不断往桌上端新菜，之前的菜还在，最后能拍到整桌；虚拟列表像只有一个窗口的传送带，旧菜撤下去、新菜送上来，窗口里始终只有几盘。等传送带停下再拍照，只能拍到最后一屏。

**准确解释**：

- 浏览器把 HTML 解析成 DOM（页面节点树）。长列表为了流畅，常只渲染视口附近的一小段；滚动时由脚本创建新行，并移除或复用离开视口的旧行。这种技术常叫虚拟列表（virtual list）、虚拟滚动（virtual scrolling）或窗口化（windowing）。
- 本项目把“旧行从 DOM 消失、换成新行”的形态叫**替换式虚拟列表**，adapter（站点适配器）的 `recycled > 0` 是候选信号；旧行一直保留、DOM 越来越长的叫**追加式列表**，`recycled` 应保持 0。“替换式虚拟列表”不是严格的行业标准名，而是本项目为了和追加式区分的写法；技术上通常统称虚拟列表或虚拟滚动。
- 采集替换式列表时，每滚一批就抽取一次，用 SKU、商品 ID、canonical（规范网址）等**稳定 ID** 去重累积；等滚到底再读最终 DOM 会漏掉前面的批次。停止条件通常是连续若干批没有新 ID，或达到滚动／时间预算。
- 如果滚动后地址栏变成可稳定访问的 `?page=N` 或 `/page/N`，先改用页码或 next 链接直接取页；交互只在 URL 不可寻址或内容确实依赖替换式列表时才需要。

| 形态 | 页面表现 | 滚到底后的 DOM | 采集要点 |
| --- | --- | --- | --- |
| 普通分页 | 点页码或 next 换一页 | 当前页 | 直接请求各页 URL，最稳 |
| 追加式无限滚动 | 越滚越长，旧条目仍在 | 通常含全部已加载条目 | 可以按批记录，也可以最后统一读；`recycled=0` |
| 替换式虚拟列表 | 行数基本不变，内容在换 | 只含最后一批或当前窗口 | 每批抽取，按稳定 ID 累积；`recycled>0` |

**常见误解**：

- “页面能一直往下滚”不等于虚拟列表。很多站只是追加式无限滚动，旧条目仍在 DOM 里。
- “DOM 里只有十几行”不等于没有数据或页面坏了；可能只是虚拟列表只渲染了窗口附近。
- “滚到底再抓一次”对追加式可能可行，对替换式会漏数据。
- “虚拟列表一定用某个库”不对。`react-window`、`react-virtualized`、`virtua` 等只是线索；最终看滚动时旧行是否消失、`recycled` 是否大于 0，以及首尾条目是否变化。
- “`recycled > 0` 就一定采全”也不对。还要看稳定 ID 是否可靠、是否真的滚到末尾、是否因预算或失败提前停止。

**本项目现状**：

- 声明式 `load_more`／`infinite_scroll` 只支持追加式列表；本地 fixture、内部容器 fixture 和 `scrapingcourse.com` 公开练习页已有有界证据。
- 替换式虚拟列表按 [ADR 0007](adr/0007-规则层与爬虫框架边界.md) 走 `hybrid`（规则声明 + 包内 adapter）：本地 fixture 12／12，`app run` 端到端 12／12；adapter 输出 `rendered`／`recycled` 指标。
- 2026-11-22 的候选扫描观察了 18 个站点，没有找到替换式 DOM；`tissus.net` 和 `mercerine.com` 是真实 JS 渲染列表，但不是虚拟列表证明（`recycled=0`）。证据见 `experiments/d07/virtual-list-scan/`、`tissus-adapter/`、`mercerine-adapter/`。
- 按当前业务判断，这类站点预计较少，因此不主动寻找真实站点补测，也不作为 v1 阻塞项；遇到实际目标再验证。现有结论只到本地 fixture、公开练习页和 adapter 契约，不写成真实替换式列表已验证。

**负责人可以追问**：

- 这个列表是追加式还是替换式？滚动时旧条目会不会从页面上消失？
- 有没有稳定的商品 ID／SKU／canonical 可以用来累积和去重？
- 滚动后 URL 能不能直接打开对应页？能的话为什么还要用浏览器？
- 停止条件是什么？连续几批没有新 ID、最多滚多少次、最多花多少时间？
- 现在的证据是本地 fixture、公开练习页还是目标站？不要把前两者写成目标站验收。

## 单实例锁与租约的区别

| 维度 | 单实例锁 | 租约 |
| --- | --- | --- |
| 目的 | 防止同一账本被两个 worker 进程同时打开 | 在多 worker 之间分配任务或工作项的所有权 |
| 粒度 | 整个账本或整个 worker 进程 | 单个任务或工作项 |
| 失效方式 | 进程退出、锁文件删除或人工处理 | 到期或心跳超时后自动可被接管 |
| 崩溃后 | 依赖启动对账，不能自动判断每一项归谁 | 过期后可被其他 worker 接管，但必须拒绝旧持有者写入 |
| 当前状态 | 已实现，仍是默认 | 单机跨进程已实现；跨机为 v1 外 |
| 适用场景 | 单机、单 worker | 多进程、多机或需要细粒度接管 |

单实例锁仍是默认安全带：它保证只有一个 worker 进程消费同一账本，避免两个进程同时改 SQLite。它不解决“哪个任务归哪个 worker”，也不支持另一台机器接手。加 `--allow-multi-worker` 后由租约分配任务；同一时刻仍只有一个合法持有者，但不同进程可以并行处理不同任务。

## 任务账本、心跳和对账

- **任务账本**：保存任务、工作项、状态、尝试次数和计数的持久记录，是状态真源。它不是线程内存，也不是爬虫框架自己的缓存目录；缓存可以丢，账本不能丢。当前用 SQLite，表包括 `tasks`、`task_items` 等。
- **心跳**：执行器定期写入的存活信号。过期只表示“这个执行器可能已经不在了”，不等于任务失败，也不等于在途项完成。租约续期通常会用到心跳。
- **对账**：重启或接管时，把账本、在途项、输出和资源对齐的过程。典型处理是 `IN_FLIGHT` 回 `PENDING`，或按尝试次数上限转 `FAILED`；同时检查计数、临时文件和方案版本。对账不是重跑，也不把未知在途当成成功。

三者关系可以记成：账本记录事实，心跳判断持有者是否还活着，对账在重启或接管时修正不一致；租约则把“谁有权写”变成账本里可检查的条件。

更多状态和恢复语义见[任务状态与计数契约](09-任务状态与计数契约.md)和[采集规则与任务运行时](19-采集规则与任务运行时.md)。

## 测试分层与 fixture

| 层 | 证明什么 | 不证明什么 | 运行方式 |
| --- | --- | --- | --- |
| T1 契约与单元 | manifest／Schema、正则语义、CSV、计数、状态转移、原子写 | 真实站点行为、浏览器、并发资源回收 | 无网络，每次改动都跑 |
| T2 fixture 集成 | discovery 来源、并行、暂停／取消、恢复、重试分类 | 真实站点覆盖、反爬、长期漂移 | 本地 fixture，每次改动都跑 |
| T3 有界实站验证 | 声明范围内的真实响应、字段来源、停止原因 | 全站覆盖、长期稳定、跨环境 | 手工，按预算和证据要求 |
| T4 生产验收 | 最终制品上的合约、状态、CSV、安全边界和用户旅程成立 | 未测站点或未声明范围 | D01／D09，独立记录与签字 |

**fixture** 是固定的本地测试页面、响应或数据，用来让测试可重复、不依赖网络。它不是真实站点证据；T2 通过只说明本地集成路径成立，不说明真实站点可采。

**常见误解**：

- “测试全绿”只证明被覆盖的范围。先看是 T1、T2 还是 T3／T4，再看没覆盖什么。
- T1／T2 是开发侧证据；T3／T4 是独立验证和验收，不能用前者的通过替代后者。
- 当前 `app` 的自动化测试以 T1 和 fixture 为主；跨进程租约有 T1／T2 和本机双进程冒烟，浏览器 adapter 有渲染 fixture 和真实站点／强杀接管证据；真实站点长期稳定性仍需要更高层验证；跨机浏览器配额为 v1 外；单进程／跨进程槽位已有 T1。

测试命令、必测项和当前差距见[测试策略](23-测试策略.md)。

## 常见误解速查

| 容易误解 | 实际含义 |
| --- | --- |
| “切片”是把数据切一部分 | 是开发增量；数据切分应写“分片” |
| “两站切片”是把两个站的数据分开 | 是用两个站验证同一条路径，不是数据分区 |
| “租约”等于多进程锁 | 单机跨进程租约已实现，但默认仍由单实例锁限制；跨机为 v1 外 |
| “worker”就是任务 | worker 是执行者；任务是有生命周期和计数的采集实例 |
| “线程池”等于多进程 | 线程共享进程；崩溃隔离和跨机接管能力不同 |
| v2 只是为了提高并发 | v2 首先是每任务进程／worker 池的隔离和稳定性；并发仍受槽位、配额和限速约束 |
| 每任务进程就是每任务线程 | 进程有独立内存和崩溃边界；线程共享进程 |
| worker 池就是线程池 | 线程池在单进程内复用线程；v2 的 worker 池通常是多个进程 |
| 故障隔离等于自动重试或安全沙箱 | 只限制故障影响面；重试按任务契约，安全沙箱另评估 |
| “批次启动”就是“同时运行” | 只是批量入队；并发由 `max_tasks`／`max_browser_tasks` 决定 |
| “`max_tasks`”是站点数或队列长度 | 是 worker 的任务槽位；批次站点数和队列长度是另外两个维度 |
| “规则写好”就能采 | 还需要规则包可用、站点状态为 `ready` |
| A20 通过等于 3+ 站点并行已验证 | A20 只覆盖两个任务；3 个及以上未单独验收 |
| “T1／T2 通过”等于真实站点可用 | 只证明本地契约和 fixture；真实站点要看 T3／T4 |
| “账本”是缓存 | 账本是状态真源；缓存可以丢，账本不能丢 |
| “能无限滚动”就是虚拟列表 | 无限滚动可能是追加式；虚拟列表的关键是旧行被移除或复用 |
| 虚拟列表滚到底再抓一次就行 | 最终 DOM 只有最后一批；必须逐批按稳定 ID 累积 |
| “线框确认”就是最终验收 | 只确认页面结构、信息层级、状态和取舍；视觉、响应式、实机验收仍要单独做 |
| 页面已实现或截图通过，就等于设计已确认 | 实现不能反推设计合理；技术预览、截图和测试通过都不等于项目方确认 |
| 原型就是最终实现 | 原型用于验证流程和交互，低保真或高保真都可以；不要求真实后端和完整异常处理 |
