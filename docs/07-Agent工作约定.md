## 文档、Skill与代码如何分工

**本目录的普通文档是主要阅读与维护入口。** Skill是可选的Agent工作入口，不是业务规范必须采用的存放形式，更不能把尚在探索的原项目执行方式冻结给新团队。

| 内容 | 建议归属 | 理由 |
| --- | --- | --- |
| 业务目标、数据标准、流程和验收 | 普通项目文档 | 人和不同Agent都可读；换框架／工具不改变业务结果 |
| 通用分析、发现、故障和质量经验 | 方法指导文档 | 可直接分发、审阅和演进，不依赖某个harness(Agent宿主) |
| 触发条件、先读哪些文档、调用什么实际工具、交付位置 | 薄Skill入口 | 当使用方需要自动发现／按需加载时才添加，避免重复正文 |
| 通用获取／浏览器／进程／重试代码 | 工具库、独立模块或服务 | 应有接口、依赖、测试和版本；调用方可以是程序、CLI或MCP |
| 一次性轻量辅助脚本 | 可按需要附在Skill | 小型脚本不必一概迁出；成为主要运行能力后按工具代码管理 |
| 具体网站分页、字段和必要交互 | 站点采集方案 | 随站点版本维护，不塞入共享引擎或Skill正文 |

新团队不必复制“方案开发Skill＋发现Skill”的原划分。可以用一个薄入口链接两类方法，也可由上游工具Skill和普通文档组合提供；以Agent能找到正确资料、实际试跑、交付可靠方案为验收依据。

## Scrapling等上游工具的采用边界

截至本文档取证日，Scrapling官方说明其Agent Skill用于教编码助手使用库，MCP(模型上下文协议)用于暴露HTTP／浏览器工具；官方Skill同时说明命令／MCP不覆盖全部可编程能力。它们可以优先评估，但仍须按实际安装版本核实，不能以文档有功能代替项目实测。

因此建议构建期按需使用上游Skill／MCP及自有业务文档，正式已验证方案直接使用成熟库／框架执行。MCP不必成为正式执行依赖，也不要求全站逐页往返Agent。出处和事实边界见[来源与维护](来源与维护.md)。

开放的`resilient-browser-fetch`保留为固定版本的可选参考资产，该源版本的分层判断与回收经验已写入方法文档；不要求继续维护其完整封装，也不把原项目旧副本当成唯一标准。

## 构建任务应提供什么

- 原始入口、目标范围、市场／语言、资源与访问边界。
- 固定数据标准及当前例外，避免让Agent逐站设计字段。
- 已有方案与真实站点证据索引，明确哪些只是线索。
- 实际可用的请求、浏览器、观察、试跑及验证工具；明确工具结果和错误结构。
- 候选方案交付位置、启动接口、预期输出和本次允许修改的文件。

路径、工具名、命令和接口由新团队设计，不能从网页内容或模型建议自动获得宿主权限。权限必须由实际运行边界执行，不能只写“请勿越权”。

## 一次构建的公开工作记录

1. 说明观察到的有效证据和需要补充的材料。
2. 说明方法与字段来源选择，使用实际工具观察、试跑和修订。
3. 反馈每次试跑的样本／字段／具体错误，保留各模板有效方法。
4. 交付完整候选、验证结果、依赖、适用限制和未解决问题。

正常工作记录不保存私有逐步推理、密钥、Cookie或网页全文；工具实际结果与Agent自报区分。候选仍需独立的程序／质量检查，不能靠自己改样本或宣称验证通过取得执行资格。

## 维护薄入口的判断

只有普通文档与工具接入不足以让Agent稳定找到并执行正确流程时，再加项目Skill。薄入口引用规范和工具接口，不另复制一套字段表、长安装教程或通用浏览器引擎。上游能力已覆盖的代码不重复包装；独有的业务控制、字段质量或故障边界才留在本项目。
