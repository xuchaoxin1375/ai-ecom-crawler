## 状态与适用范围

**Accepted**（2026-11-20）。R16 已验证任务账本、两任务并行、暂停／恢复／取消、单 worker 强杀恢复和启动对账；跨进程 worker 需要租约后再扩展，单 worker 仍是当前边界。

本文决定采集任务的状态真源、控制方式、存储和并行模型，不改写业务口径。任务生命周期、计数和结果字段以 `09` 为准；规则形式以[采集规则形式与阶段模型](0002-采集规则形式与阶段模型.md)为准；运行设计详见[采集规则与任务运行时](../19-采集规则与任务运行时.md)。

## 背景与约束

- 最终目标：多个采集任务并行运行，并且能暂停、恢复、取消和观察。
- 早期实现可以简单，但不能堵死进程化、多 worker 和后续 UI。
- 单用户、单执行机；Windows、Linux、WSL2。
- 静态 HTML 先跑通，浏览器和适配器后置。
- 软件栈免费／开源、可自托管；v1 不引入 Celery、Temporal、Redis 或 RabbitMQ。
- 任务状态不能依赖 Scrapling 的 `crawldir` 或线程内存；必须有可对账的自有账本。

## 决策

1. **任务是运行实例，不是规则的一部分**：`task_id`、`rule_id`、`rule_version`、`task_type`、输入、限制、输出和状态写入任务账本。
2. **任务账本是状态真源**：SQLite WAL 保存任务和工作项；Scrapling／浏览器缓存只作执行层缓存。
3. **工作项是检查点、重试和并行的最小单位**：按 `(task_id, item_type, normalized_url)` 幂等；每个工作项完成后落状态。
4. **v1 用单进程 + 线程池 + SQLite WAL**：默认 2 个任务并行，每任务 2 个 product worker；全局按域名限速；静态 HTTP 足够。
5. **控制在工作项边界生效**：暂停停止派发，在途结清后进入 `PAUSED`；取消停止派发并拒收迟到结果；恢复从检查点继续。
6. **每任务隔离**：独立状态、计数、输出目录、会话和事件文件；全局只共享限速、并发上限和资源槽。
7. **分阶段演进**：v1 单进程线程池；v2 每任务进程／worker 池；v3 外部队列。任务和工作项契约不变。

## 存储

v1 SQLite 表：

- `tasks`：任务、方案版本、类型、状态、预算、计数、起止时间；
- `task_items`：工作项、阶段、状态、尝试次数、父 URL、结果摘要；
- `task_events` 可后置；v1 先写每任务 `events.ndjson`。

约束：

- WAL 模式，短事务；不在事务里发 HTTP；
- 不把整页 HTML 或大字段写进任务库；
- 商品记录写每任务 `products.jsonl`，结束时导出 9 列 CSV；
- 多任务并行时各写各的任务目录，SQLite 只做状态更新。

出现多 worker 写竞争、多用户或远程执行时迁 PostgreSQL；迁移前不引入第二套状态真源。

## 并行与调度

| 版本 | 形态 | 触发条件 |
| --- | --- | --- |
| v1 | 单进程，线程池，SQLite WAL | 本地单用户、静态 HTTP |
| v2 | 每任务进程／worker 池 | 浏览器、适配器、故障隔离 |
| v3 | 外部队列 + 多 worker | 多机、大量任务、远程执行 |

v1 的全局资源：

- `max_concurrent_tasks`：同时运行的任务数；
- 每域名限速器：所有任务共享，避免两个任务同时打一个站；
- 每任务并发：navigation／product 分开；
- 全局最大请求数和内存上限。

公平性：

- 调度器按任务轮转领取工作项，不让一个任务长期占满 worker；
- 工作项队列有界；导航发现遇到背压时暂停，不无限堆积；
- 任务暂停／取消不阻塞其他任务；
- 全局限速不因任务优先级被绕过。

## 2026-11-20 补充：暂停、取消与崩溃恢复

- 暂停可恢复：停止派发，在途结清，`PAUSING` → `PAUSED`；恢复从工作项检查点继续，不承诺恢复浏览器内存。
- 取消是终态：`CANCELLING` → `CANCELLED`，迟到结果拒收，资源回收；继续采集必须新建任务。
- 崩溃不是状态：重启先对账；`IN_FLIGHT` 回 `PENDING` 或 `FAILED`；不把未知在途当成功。
- 工作项 `FAILED` 是终态；临时失败在 `max_attempts` 内回 `PENDING`，结果写 `failure_class`（`transient`／`permanent`／`blocked`），不新增 `FAILED_TRANSIENT` 状态。
- 提交顺序：结果持久化后再标记 `DONE`；文件用临时文件＋rename；重试按幂等键覆盖，不重复计数。
- 恢复条件：`plan_id`／`plan_version`、市场、环境和配额兼容；不兼容时新建任务。
- 运行字段 `rule_id`／`rule_version` 映射对外 `plan_id`／`plan_version`，不对外暴露两套版本。
- 实现状态：R16 原型只覆盖 5 个工作项状态和 `reset_in_flight`；`failure_class`、尝试次数封顶、原子写和孤儿回收待补，详见[采集规则与任务运行时](../19-采集规则与任务运行时.md)。

## 为什么不选其他方案

- **先做 FastAPI 服务和 Web UI**：会先花时间在接口和界面上，核心任务账本和并行语义还没验证；CLI 先跑通，服务后续包装同一任务层。
- **Celery／Temporal／Redis／RabbitMQ**：单用户单机用不上，增加部署和状态对账成本；多机或大量任务时再引入。
- **每任务一个子进程作为 v1 默认**：隔离好，但静态 HTTP 阶段进程启动和 IPC 成本不必要；v2 在浏览器／适配器场景启用。
- **直接用 Scrapling Spider 的队列和 `crawldir`**：抓取层恢复不等于 `09` 的任务状态、计数和取消语义；任务真源必须自有。
- **只做单任务 CLI**：能跑，但不能验证多任务并行、全局限速和任务隔离，后续会返工。

## 后果

- 需要任务账本、工作项状态机、调度器、全局限速器和输出隔离。
- SQLite 写竞争是 v1 的现实约束；短事务、每任务文件和合理的任务并发可以控制。
- 暂停／取消／恢复需要测试，尤其是崩溃后 `in_flight` 工作项的对账。
- CLI 和未来服务共享同一个 `TaskStore` 和执行核心，不出现第二套业务逻辑。
- 迁移到进程或队列时，规则、工作项和任务结果不需要重写。

## 跟进

- 按[采集规则与任务运行时](../19-采集规则与任务运行时.md)实现最小运行时切片。
- 验证：discovery 与 product 两任务并行、同域限速、暂停／恢复／取消、崩溃恢复。
- 记录 SQLite 写延迟、任务启动延迟和每任务资源占用；出现持续竞争再评估 PostgreSQL。
- 浏览器和适配器接入前，先补子进程隔离和资源回收测试。
