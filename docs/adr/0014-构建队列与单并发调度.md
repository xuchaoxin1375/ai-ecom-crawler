## 状态与适用范围

**Accepted**（2026-11-24）。本 ADR 扩展 [ADR 0005](0005-构建Agent与Harness契约.md) 和 [ADR 0006](0006-构建Harness选型与集成方式.md) 的 v1 单会话边界：仍然一次只运行一个构建，但允许其他站点提交后排队，而不必收到 `409` 后手动重试。

不改变 Harness 进程模型、单 worker、单出口和单用户边界；不引入优先级、多 worker 或并发构建。跨重启会话恢复由 [ADR 0015](0015-构建会话跨重启恢复.md) 扩展；本 ADR 中“不恢复运行中会话”的描述以 0015 为准。

## 背景

2026-11-26 补充决策（Provisional）。在现有单服务、SQLite 队列和 OpenCode HTTP/SSE 栈内实施可选的构建并发。每个活动构建独占一个 `BuildService` 和 OpenCode 实例，从领取到主机验证及收尾结束占用槽位。共享规则安装和依赖安装分别串行写入。已有会话恢复和自动采集入队继续使用原账本。默认 1，回退到 1 即可恢复单槽运行。配置与验收见[规则分析并发](../37-构建Agent-Harness集成与使用说明.md#规则分析并发提案)，完成双会话、重启和资源回收实测后复审。

v1 的全局单构建限制把“同时只能跑一个”直接映射成“第二个请求必须失败”。这在多站点接入时有两个问题：

- 用户需要守着前一个构建结束再手动提交，跨站点提交被 409 打断。
- 服务重启时所有 `CREATED`／`RUNNING` 构建都被标记失败；即使请求只是排队，也会丢失。

## 决策

- **单并发、FIFO 队列**：全局只有一个运行槽位；`QUEUED` 不占槽位，按插入顺序等待。同一站点仍最多一个活跃构建（含 `QUEUED`），重复提交同一站点仍返回 `409 BUILD_CONFLICT`。
- **状态扩展**：构建账本新增 `QUEUED`。它表示请求已持久化、站点已占用，但尚未创建 Harness 会话。`CREATED` 及之后的状态仍表示会话已创建。
- **请求持久化**：入队时把规范化参数写入 `builds.request_json`，包括预算、修复轮数、代理、归档／目录配置、robots 结果、修复原因和原站点 readiness。重启后按同一参数启动，不依赖进程内字典。
- **调度时机**：入队后若槽位空闲立即启动；否则等待当前构建结束、取消或失败后由 watcher 触发下一个。启动前重新检查站点状态、规则文件、源规则哈希和活跃任务，条件失效时记录失败并继续下一个，不空转。
- **反馈回落**：排队或运行中的修复被取消、失败或重启中断时，关联反馈从 `REPAIRING` 放回 `TRIAGED`，不留下永久修复中的反馈。
- **排队取消**：`QUEUED` 可直接取消，不调用 Harness；释放站点并立即调度下一个。`pause`／`resume` 只对已启动的构建有效。
- **重启语义**：`reconcile` 仍把已创建会话的 `CREATED`／`RUNNING`／`PAUSING`／`PAUSED`／`CANCELLING`／`VALIDATING` 标为中断失败；`QUEUED` 保留并在 reconcile 末尾启动最旧一条。`shutdown` 同样只失败运行中的构建，保留排队项。
- **只读预览**：`ECOM_BUILD_DISABLED=1` 时不调度队列，避免只读实例意外启动付费模型会话。
- **手动继续**：失败构建的 continue 仍占用同一个槽位；另一个构建运行中时拒绝，槽位空闲时可以运行，不插入队列顺序。

## 实施

- `app/src/ecom_crawler/builds.py`：`_drain_queue()`、`_launch_queued()`、`_queue_precondition_error()`、`RUNNING_BUILD_STATES`、`_slot_build_id`、`reconcile()`／`shutdown()`／`cancel()`。
- `app/src/ecom_crawler/runtime/models.py`：`BUILD_STATES` 和 `BuildRecord.request`。
- `app/src/ecom_crawler/runtime/store.py`：`request_json` 列与迁移、按插入顺序的队列查询。
- 前端：`QUEUED` 状态标签、队列位置、取消排队和站点下一步提示。

## 后果

- 多站点接入可以连续提交，不必盯守前一个构建；请求参数跨重启可恢复。
- 单 worker 和单出口仍然限制吞吐；排队时间可能较长，且没有优先级或过期策略。
- 失败构建的会话仍只在内存中保留，跨重启后不能 continue；本轮只恢复排队项。
- `QUEUED` 站点保持 `building` readiness，任务启动、激活、回滚和复跑继续被站点忙守卫阻止。

## 替代方案

- **保持 409 手动重试**：实现最少，但多站点提交被反复打断，重启仍会丢失等待请求。
- **按站点分别排队**：能避免跨站点互相等待，但仍受全局单 Harness 限制，只是把排队复杂度移到调度器；留到多 worker 时再评估。
- **直接并发多个 Harness 会话**：吞吐更高，但需要独立工作区、出口、资源配额和失败隔离，超出当前单 worker 边界。
- **把所有活跃构建在重启后自动重跑**：会把已消耗的模型调用和副作用重新执行一遍，费用和重复写入风险不可控；本轮只恢复尚未开始的排队项。
