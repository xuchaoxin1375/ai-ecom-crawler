## 状态与适用范围

**Accepted**（2026-11-20）。R16 已用声明式规则跑通两个站、discovery／product 切片、schema 校验和第二个站只加规则包的复用；复杂交互仍按本文走 adapter 或 hybrid。

本文决定采集规则的形式、阶段划分和工作项模型，不改写业务口径。字段、价格、描述仍以 `02` 为准；方案包外壳以 `08` 为准；任务状态和计数以 `09` 为准。运行设计详见[采集规则与任务运行时](../19-采集规则与任务运行时.md)。

## 背景与约束

- 项目方经验：旧流程约 90% 的站能处理，简单站快、复杂站多花时间；不再追每站精确工时。
- AI 分析站点和生成规则不是主要瓶颈；**规则怎么表达、怎么组织、怎么执行**才是重点。
- 规则至少要覆盖：网址发现、有效请求到页面内容、产品数据提取。
- 有的站只需要发现网址，不需要产品提取；规则不能强制所有任务都走完整产品链路。
- 最终要支持多个任务并行；每个阶段要能独立控制和观察。
- 早期实现可以简单，但不能堵死后续的进程化、并行化和复杂站点适配。
- 软件栈继续遵守免费／开源、可自托管（J03）；运行期不逐页调用 LLM。

## 决策

1. **规则形式采用声明式优先的混合模式**：`kind` 取 `declarative`、`program` 或 `hybrid`。常规站用 YAML 描述；复杂交互或站点特例用包内 adapter，adapter 不接管任务状态和控制。
2. **规则按阶段组织**：`discover`、`fetch`、`extract`、`validate`、`output`。阶段是处理逻辑和预算的单位，不是必须一次性串行跑完的黑盒。
3. **运行时以工作项为最小单位**：`navigation` 和 `product` 两类工作项；每个工作项有状态、阶段、尝试次数和检查点。并行、重试、暂停和恢复都落在工作项边界。
4. **任务类型显式**：`discovery` 只做导航和 URL 判型，输出 URL 清单；`product` 继续抓取、提取和校验。规则可以同时支持两种任务；纯发现规则可以省略 `extract`。
5. **方案版本化，任务绑定版本**：规则包有 `rule_id` + `rule_version`；任务只引用版本，不修改规则。规则变化不回头改写旧任务。
6. **输出显式**：`url_list` 和 `product_csv` 是两种独立输出；product 任务可以附带 URL 清单，discovery 任务不抓商品页。
7. **运行期确定性**：普通批次不逐页调用 LLM；AI 只在构建期生成和修订规则。

## AI 构建边界（2026-11-20 补充）

- AI 只在构建期工作：分析站点、生成和修订规则包、试跑；执行期普通批次零 LLM 调用。
- 规则形式维持声明式优先＋adapter；adapter 只处理复杂公开交互，不接管任务状态、计数、暂停／取消和资源回收。
- 规则包版本化：`plan_id`／`plan_version` 为对外契约；运行实现 `rule_id`／`rule_version` 映射到它。规则实质变化递增版本，不热改正跑任务。
- AI 生成或修复规则后，旧任务不原地恢复；新版本建新任务，旧结果保留。
- AI 生成的程序在子进程或受控环境执行，不 import 进主服务；不携带密钥、Cookie、profile；不绕过登录、付费或访问控制。
- 人工复核和证据：样本、字段核对、9 列 CSV、`task-result.json`；AI 自报不算验收。
- 当前证据：D01 试点已签字（有条件通过）；R16 两站、sitemap／分页／next／HTML 索引／公开 JSON 已跑通；动态／复杂分页仍走 adapter 或后置。

## 规则包结构

```text
rules/<site>/
  manifest.yaml          # 规则入口
  adapter.py             # 可选；program/hybrid 时使用
  samples/               # 可选；合成样本或获准的样本网址
  README.md              # 可选；运行和边界说明
```

`manifest.yaml` 分节：

- `site`／`scope`：站点、入口、允许的 origin／路径、市场、语言、币种。
- `capabilities`：`discovery`／`product`；`product: true` 时必须有 `extract`。
- `discovery`：入口链接、sitemap、分类、分页、URL 判型、身份去重和发现预算。
- `fetch`：静态／浏览器／公开 JSON、并发、限速、重试、超时、robots 和挑战策略。
- `extract`／`normalize`／`validate`：字段回退、清洗、正价和币种校验；纯发现规则可省略。
- `output`：URL 清单和／或 9 列商品 CSV。
- `task_defaults`：数量、时间和并发默认值。
- `compatibility`／`evidence`：运行环境和证据状态。

规则先复制基础模板，站点差异写进规则包；模板继承／合并后置，等复制成本真的成为问题再加。

## 工作项与阶段

| 工作项 | 处理 | 产出 |
| --- | --- | --- |
| `navigation` | 入口页、sitemap、分类、分页、公开 JSON | 更多导航项或商品 URL |
| `product` | 商品页 fetch、extract、validate | 商品记录或 URL 清单条目 |

工作项状态：`PENDING`、`IN_FLIGHT`、`DONE`、`EXCLUDED`、`FAILED`。幂等键为 `(task_id, item_type, normalized_url)`。

阶段控制至少包括数量、时间、请求数、并发、重试和连续失败停止；阶段可以单独运行，用于只验证发现或只验证提取。v1 允许一个 product 工作项在同一线程内完成 fetch→extract→validate，但记录阶段和耗时，后续可拆成独立 worker。

## 为什么不选其他形式

- **纯声明式**：简单站够用，但复杂公开交互和分支会把 schema 撑成事实上的 DSL，最后既难写也难调。
- **纯程序**：灵活，但目标用户是“懂业务、会配规则但不写代码”的技术运营；每站写脚本会退回旧工具的手工维护模式。
- **固定线性流水线**：网址发现本身要发请求（分类页、分页），严格的 discover→fetch 串行会卡住；工作项模型更贴合真实抓取。
- **自定义 DSL**：表达力更强，但学习、解析、调试和 AI 生成成本都高；v1 不值得。
- **直接把 Scrapling Spider 当规则和任务模型**：Spider 的队列／`crawldir` 不能替代 `09` 的任务状态和计数；Scrapling 只作为获取和解析能力，任务真源在自有账本。

## 后果

- 需要规则 schema 校验、阶段处理器、工作项状态和发现／产品两种输出。
- 规则包会比单一 manifest 多几个字段，但站点侧仍然只写声明式规则。
- 复杂站保留 adapter 逃生口；adapter 必须通过子进程或明确接口接入，不能绕过任务状态。
- 纯发现任务成为一等公民，不再被迫写商品字段。
- 第二个站要验证“只改规则、不改运行时”；如果必须改运行时，记录为规则表达缺口。

## 跟进

- 按[采集规则与任务运行时](../19-采集规则与任务运行时.md)实现最小切片：同一规则包跑 discovery 和 product 两个任务。
- 补 JSON Schema 和规则校验器；未知字段和未知版本拒绝加载。
- 第二个站复测规则复用；记录声明式覆盖率、适配器需求和运行时缺口。
- 运行稳定后再评估规则继承、模板合并和更多发现策略。
