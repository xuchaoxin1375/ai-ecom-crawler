## 状态与适用范围

**Proposed**。项目方于 2026-11-20 确认按“规则层负责计划、框架层负责执行”的方向评估复杂网址发现；2026-11-21 `app` 已实现 C1 的 `load_more`／`infinite_scroll` v0 并在公开练习页取得有界证据；2026-11-22 补了最小虚拟列表 hybrid adapter 并接入 `app run`（本地端到端 12／12），但 Crawlee／Scrapy 框架 adapter 的同条件对照仍未执行，验证后再转 Accepted。G0（2026-11-20）保留 Proposed；复杂交互仍走 C2 adapter。退出条件：完成 load-more 对照并明确 primitive 取舍。

本文决定规则系统与爬虫框架的职责边界，不改变业务口径、方案最小字段、任务状态和计数。方案包见[采集方案与兼容契约](../08-采集方案与兼容契约.md)，运行时见[采集规则与任务运行时](../19-采集规则与任务运行时.md)，发现策略见[网址发现与分页策略](../22-网址发现与分页策略.md)，框架对比见[框架对比实验](../13-框架对比实验.md)。

## 背景与约束

- 静态发现（sitemap、HTML 索引、页码、next、公开 JSON）已经能用声明式规则表达，R16 的 sitemap 和 `page_param` 也已有真实站点证据。
- `load more`、无限滚动、虚拟列表等复杂交互，本质是浏览器生命周期、点击／滚动、等待条件、会话、重试和资源回收问题，不是 URL 模式问题。
- 把这些能力全部塞进声明式 DSL，会把规则 schema 变成一门不完整的编程语言：难写、难校验、难排障，运行时还要重复实现框架已有的队列、浏览器和恢复能力。
- 直接用框架代码处理所有站点，又会丢掉规则层的范围、上限、证据、版本和跨执行端复用；AI 生成代码后的验证成本也更高。
- 项目已经有 `kind: declarative`、`program`、`hybrid` 三种方案形态；R16 目前只实现 `declarative`，不应为了复杂交互把它扩成通用浏览器引擎。
- 软件栈继续遵守免费／开源、可自托管（J03）；运行期不逐页调用 LLM。

## 决策

### 两层分工

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 计划层（规则／manifest） | 来源、范围、URL 判型、字段映射、上限、停止条件、证据、方案版本、任务类型 | 浏览器生命周期、请求队列、并发、重试、会话、存储、资源回收 |
| 执行层（框架／adapter） | HTTP／浏览器、点击／滚动、等待、队列、并发、重试、会话、暂停／取消、资源回收 | 业务范围、字段口径、验收结论、任务状态和计数的所有权 |

规则层把计划编译成执行层的请求或处理器；执行层把页面、URL、字段、停止原因和资源状态回写给规则层。两者通过有版本的 adapter 契约连接，不互相 import 内部实现。

### 能力分层

| 层级 | 能力 | 归属 | 默认 |
| --- | --- | --- | --- |
| C0 静态发现 | sitemap、HTML 索引、页码、next、公开 JSON、嵌入式 JSON | 规则层 | 声明式 |
| C1 固定交互 | 单个 `load_more` 按钮、单个容器的无限滚动 | 规则层 primitive + 执行层浏览器 | v0 已实现，有界使用；对照待补 |
| C2 复杂交互 | 虚拟列表、网络请求重放、多步状态、登录／CSRF、GraphQL、站点特定等待 | 执行层 adapter／`hybrid` | 框架优先 |
| C3 访问控制 | 登录、付费、验证码、401／403、挑战页 | 人工／停止 | 不自动绕过 |

C1 最多保留两个 primitive：`load_more` 和 `infinite_scroll`。它们只表达“触发方式、等待条件、批次上限、无新条目停止”，不提供任意 JS 执行、任意点击序列或站点脚本。超过这个范围就进入 C2，不再扩 DSL。

### 判定规则

- 能用现有来源、推进、停止和证据字段表达 → 声明式规则。
- 需要虚拟列表、网络捕获、多步状态、登录／CSRF／GraphQL、站点特定等待或自定义 JS → `hybrid` adapter／`program`。
- 如果目标站点里 C2 占多数，转为框架优先：框架做执行引擎，规则层退化为范围、字段、预算和验收契约。
- 新增 primitive 前必须有同条件对照和两个以上站点的重复需求；不能因为单个站的特殊交互扩 schema。

### Adapter 契约

`hybrid`／`program` 方案至少声明：

- `plan_id`／`plan_version`、`adapter_id`／`adapter_version`、`capabilities`、`entrypoint`、`compatibility`；
- 输入：入口、范围、上限、市场／语言／币种、必要的会话或 profile 标识；
- 输出：发现的 URL／商品、页数、请求数、停止原因、`last_page_verified`、错误分类、资源回收结果；
- 证据：样本 URL、字段来源、页面层级、失败原因；不保存整页 HTML、密钥、Cookie 或浏览器 profile；
- 边界：adapter 不拥有任务状态、计数、暂停／取消和最终验收；不绕过登录、付费、401／403、验证码或挑战页；不把私有 XHR 当公开 API；
- 执行：在子进程或受控环境运行，不 import 进主服务；超时、内存、浏览器实例和临时目录有上限。

adapter 的站点差异必须版本化；同一 `plan_version` 不热改正在运行的任务。adapter 失败时回写结构化错误，不把半成品当结果。

### 框架选型

候选包括 Crawlee（请求队列、浏览器池、会话、重试）、Scrapy（成熟静态抓取＋Playwright 集成）、Scrapling（现有依赖，Spider／会话／动态获取）和 Playwright／Patchright（只做浏览器控制，需外层调度）。

本文暂不选定默认框架。先做 load-more 对照，再按以下维度选择：

- 队列、并发、重试、会话和暂停／恢复是否成熟；
- 浏览器实例、临时目录和进程能否可靠回收；
- 证据、日志和错误分类是否可回写规则层；
- 依赖重量、跨平台安装和 AI 生成／修复成本；
- 是否能被替换，退出成本是否可接受。

## 为什么不选其他形式

- **纯声明式包办一切**：简单站够用，但复杂公开交互和分支会把 schema 撑成事实上的 DSL，最后既难写也难调。
- **纯框架代码处理所有站**：复杂交互稳，但每站写代码，范围、上限、证据和跨执行端复用会散落；AI 生成后的验证成本高。
- **把框架配置直接当规则引擎**：框架配置通常绑定具体框架和运行方式，不是可移植的方案契约；需要 adapter 层把意图和执行分开。
- **只做 C1、不做 C2**：会迫使所有复杂站都走 primitive，最终 primitive 越加越多，仍然回到 DSL 膨胀。

## 影响

正向：

- 不重复实现浏览器池、队列、重试、会话和资源回收，复杂交互直接用框架成熟能力。
- 规则层继续负责范围、预算、判型、证据和验收，保持可读、可审计、可复用。
- 复杂站有明确的 `hybrid` 出口，不需要把 DSL 扩成编程语言。
- 框架可替换；adapter 契约和证据让更换执行层有验收依据。

代价：

- 需要维护 adapter 版本、契约测试和跨进程边界。
- 规则层和执行层之间多一层序列化／回写，排障要同时看两边。
- 复杂站的方案不再完全是 YAML，AI 生成和人工复核都要覆盖 adapter 代码。
- 框架选型、依赖和升级仍需单独治理。

## 验证计划

先做无验收性质的 load-more 对照，不直接改 R16：

1. 选一个公开、允许技术分析的 `load more` 或无限滚动站点，记录入口、预算、出口和请求数。
2. 变体 A：在 `app` 加最小 `load_more`／`infinite_scroll` primitive（schema 1.2），只实现点击／滚动、等待条目增加、无新条目停止和上限；2026-11-21 已完成 v0，R16 原型未改。
3. 变体 B：用 Crawlee／Scrapling／Playwright 写一个 adapter，保持同样的范围、预算和停止条件。
4. 比较构建时间、代码量、成功率、请求数、重复率、修复成本和证据完整性。
5. 只有 primitive 覆盖多数样本、代码量可控、没有自定义 JS 时才保留；否则固定为 adapter，并停止扩 DSL。

当前证据：C1 的 `load_more`／`infinite_scroll` 已在 `app` 的浏览器 adapter 上跑通本地 fixture 和公开练习页（各 15／15，约 84／88 秒），内部容器追加型另有本地 fixture 6／6；2026-11-22 补了一个 C2 虚拟列表 hybrid adapter，本地 fixture 12／12、按稳定 ID 逐批累积替换式 DOM，并接入 `app run`：adapter discovery 后由声明式 `fetch`／`extract` 完成 12／12 商品导出；另在 `tissus.net` 真实 JS 渲染列表完成 10／10 商品导出（`experiments/d07/tissus-adapter/`）。输入上下文和 NDJSON 事件契约见 `19` 与 `experiments/d07/virtual-list-hybrid/`。真实虚拟列表、浏览器实例配额和 Crawlee／Scrapy 框架对照仍未做；adapter profile 已纳入任务资源并在正常退出后删除，删除失败时做 best-effort 进程扫描。静态发现已有 R16 sitemap（S1，30 URL）和 `page_param`（S5，3 页 62 URL）。本文保持 Proposed。

2026-11-21 的浏览器 fetcher v0 同时包含**执行层渲染**和 **C1 primitive v0**：渲染按任务启动 Patchright CDP、复用一个 page、登记并回收 Chromium PID 和 profile；`load_more`／`infinite_scroll` 在规则层只声明按钮／容器、上限和停止条件，动作由执行层完成。它证明了 C1 可以由规则层表达；2026-11-22 的最小虚拟列表 adapter 原型证明了 C2 可以不扩 DSL，但 Crawlee／Scrapy 框架对照仍未执行，C1 primitive 是否长期保留仍待定。

## 开放问题

- C2 的默认执行框架选 Crawlee、Scrapling 还是 Scrapy＋Playwright？需要同条件对照。
- adapter 的打包、版本和跨设备分发方式；是否随方案包一起分发，还是按依赖安装。
- C1 primitive 的长期上限是否就是两个；出现第三个重复需求时是否直接转 C2。
- 复杂交互占目标站点多大比例时切换为“框架优先”；先用样本统计，不预设固定百分比。
- adapter 的浏览器 profile、会话和临时目录如何纳入统一资源配额和崩溃回收；v0 已把任务级 PID／profile 纳入 `task_resources`，跨进程配额仍未解决；跨机回收为 v1 外。
