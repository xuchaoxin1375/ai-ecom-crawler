## 状态与适用范围

**Accepted（当前方案）**，验证状态为 **partial**。本 ADR 确认 `app/frontend/` 的样式层继续使用手写原生 CSS 和 CSS 变量令牌，不引入 CSS 框架、CSS 预处理器或带视觉的 UI 组件库；同时把“何时重新评估 CSS 框架”写成可核对的触发条件。方案已随批次工作台阶段 1 和任务控制台进入生产路径；跨浏览器、读屏、深色／高对比主题和样式回归自动化仍未验证，因此不把验证状态写成 complete。

**2026-11-23 v2 方向**：项目方接受 React 作为新版本前端，设计基线见[前端设计系统与 v2 视觉方向](../35-前端设计系统与视觉方向.md)，技术决策见 [ADR 0012](0012-前端v2技术栈与设计系统.md)（Provisional，v2 已设为默认入口）。旧 Vue 应用已弃用，只在未迁移功能中继续按本文执行；`style.css` 已增长到 29,053 字节、1,873 行、约 226 个顶层类选择器，本文列出的“重复手写、类名冲突与回归、协作可读性、组件行为缺口”已出现。ADR 0012 完成功能对等后，本文由它修订或取代，不直接把现有应用改成 Tailwind。

本文是 [ADR 0009](0009-批次工作台前端技术栈.md) “样式与组件”条目的展开，不改变该 ADR 的 Vue 3 + TypeScript + Vite 决策，也不改变页面信息架构、组件行为或 API。视觉基线以 [D08 前端设计包](../28-D08前端设计包.md) 为准，界面范围以 [v1 界面范围](../25-v1界面范围.md) 为准。原生 `/` 兜底页仍按 [ADR 0008](0008-前端技术栈与本地Web形态.md) 执行，本文只把它作为迁移期对照，不把它扩展为第二套设计系统。

### 术语说明

- CSS 框架：提供成套类名或组件的样式方案；本文特指 Tailwind CSS、UnoCSS 这类工具类框架，以及 Element Plus、PrimeVue、Naive UI 这类带视觉的 UI 组件库。
- 设计令牌（token）：把颜色、间距、圆角、阴影等写成 CSS 变量，页面引用变量而不是重复写具体值。
- 全局样式：在应用入口引入一次、所有页面共享的 CSS；类名没有编译期作用域。
- 工具类框架：用大量短类名组合出样式，例如 `flex`、`gap-2`、`text-sm`。
- Headless 组件库：只提供交互行为和无障碍语义、不绑定视觉样式的组件库。
- partial（部分验证）：方案已实现并有页面走查证据，但跨浏览器、读屏或自动化仍不完整。

## 背景与约束

现状（2026-11-23）：

- 样式入口是 `app/frontend/src/style.css`，由 `main.ts` 全局引入；文件 29,053 字节、1,873 行（非空 1,590 行），含 31 个 CSS 变量、约 226 个顶层类选择器、5 个媒体查询和 1 组关键帧（2026-11-23 复核）。
- 11 个 `.vue` 文件（应用外壳、共享组件和 6 个路由视图）都没有 `<style>` 块，也没有使用 `<style scoped>` 或 CSS Modules；页面样式通过全局类名复用。
- `package.json` 只有 `vue`、`vue-router`、`pinia` 三个运行时依赖；Vite 配置没有 PostCSS、Sass、Tailwind 或 UnoCSS 插件；仓库没有 `tailwind.config.*`、`postcss.config.*` 或 `*.scss`。
- 旧 `/legacy` 原生页面另有 `app/src/ecom_crawler/web/static/style.css`（约 628 行、11 个 CSS 变量），令牌名称相近但取值不完全相同；它是 ADR 0010 保留的技术兜底，不再是主导航入口。

项目约束：

- 单机、单用户、内部后台控制台，页面以表格、表单、筛选、弹窗和状态提示为主，没有多品牌或多设计系统需求。
- 视觉基线已在 `28` 确认，当前只做浅色主题；深色和高对比主题后置，尚未进入 v1。
- 代码主要由 AI 生成，需要减少隐式约定和额外构建配置，样式规则要能被人工快速复核。
- 样式层已经进入生产路径，任何框架引入都要先有决策记录，不能边写边换或在一个页面里混用多套 UI 库，这一约束沿用 ADR 0009。

## 决策

- **样式写法**：继续手写原生 CSS，集中在 `app/frontend/src/style.css`，由 `main.ts` 引入一次；新增页面优先复用现有类名和令牌，不默认在单文件组件里新建 `<style>` 块。
- **设计令牌**：沿用 `:root` 下的 CSS 变量（背景、面板、文字、分隔线、品牌色、状态色、圆角、阴影、侧栏宽度、动效时长等）；新颜色和间距先补令牌，不在页面里散落硬编码值。
- **不引入 CSS 框架**：当前不引入 Tailwind CSS、UnoCSS 等工具类框架，不引入 Sass／PostCSS 预处理链，也不引入 Element Plus、PrimeVue、Naive UI 等带视觉的 UI 组件库。
- **不默认启用作用域方案**：不把现有全局类改为 CSS Modules 或 `<style scoped>`；如果出现类名冲突，先小范围评估 `scoped` 或 CSS Modules，不一次性重写。
- **组件策略**：表格、表单、弹窗和状态提示继续自建轻量组件；交互行为和无障碍缺口变大时，优先评估 headless 组件库（如 Reka UI、Headless UI 等，评估时核对当前维护状态），保留现有 CSS 令牌和视觉。
- **重新评估入口**：出现本文“重新评估 CSS 框架的条件”中的信号时，先做单页试点和方案对比，再修订本 ADR 或新增 ADR；未修订前不直接引入。

## 为什么保持手写 CSS

| 维度 | 判断 |
| --- | --- |
| 视觉一致性 | 所有页面共用一套令牌和类名，不会出现框架默认样式、组件库主题和项目主题三套视觉语言 |
| 依赖与构建 | 不增加 PostCSS、Sass、Tailwind 或组件库依赖，锁文件和升级面保持最小 |
| 页面规模 | 当前是 6 个路由视图加 3 个外壳／共享组件，表格和表单模式有限，手写的重复量还可以接受 |
| 可复核性 | 样式集中在一个文件，人工和 AI 都能按类名找到落点；令牌变更的影响面容易追踪 |
| 迁移成本 | 原生 `/` 兜底页和 Vue 应用都按原生 CSS 维护，迁移期不需要同时维护两套构建链 |
| 风险 | 全局类名没有作用域，页面增长后冲突和误覆盖风险上升；组件行为和无障碍需要自己保证 |

当前判断是：在页面规模、主题数量和协作人数没有明显变化前，引入框架的构建成本、视觉迁移成本和双轨维护成本高于收益。这个判断有明确的重评条件，不是永久排除框架。

## 备选与不选理由

| 备选 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 手写 CSS + 令牌（现状） | 依赖少、视觉统一、样式集中、与现有页面和原生兜底页一致 | 全局作用域、自建组件、样式回归依赖人工走查 | **采用** |
| Tailwind CSS | 工具类成熟、无需命名、能快速统一间距和状态样式 | 需要构建配置；长类名串降低模板可读性；现有语义类和新工具类会形成双轨 | 暂不采用；样式编写效率成为瓶颈时作为单页试点候选 |
| UnoCSS | 按需生成、配置灵活、运行时开销小 | 生态和资料密度低于 Tailwind；团队和 AI 的熟悉度需要重新建立 | 与 Tailwind 同属工具类备选，不默认引入 |
| Sass／PostCSS | 嵌套、变量、兼容前缀和旧浏览器降级 | 当前 CSS 变量和现代浏览器目标已覆盖主要需求；增加构建链和调试层 | 不采用，除非出现复杂主题或明确的兼容目标 |
| CSS Modules 或 `<style scoped>` | 零新增运行时依赖，能缓解全局类名冲突 | 需要调整现有全局类写法；跨页面共享样式仍要另有约定 | 作为类名冲突时的低成本演进，不作为当前默认 |
| 带视觉的 UI 组件库 | 表格、表单、弹窗和日期选择等组件现成 | 绑定其主题、升级节奏和可访问性实现；与现有令牌和设计包冲突，容易形成第二套视觉语言 | 不采用；只有接受整体视觉改版时才重新评估 |
| Headless 组件库 | 交互行为、焦点管理和无障碍语义现成，样式仍可沿用现有令牌 | 增加依赖和学习成本；需要自己完成视觉层 | 组件行为成为主要痛点时优先评估 |

## 重新评估 CSS 框架的条件

以下是评估信号，不是自动引入的硬性指令；命中一条或多条时，先记录具体页面、重复模式和维护成本，再决定是否做试点。

- **重复手写**：同一表格、表单、弹窗或状态模式在 3 个以上页面重复实现，差异主要是颜色、间距或列宽。
- **类名冲突与回归**：全局类名互相覆盖，或一次样式改动需要全站截图回归才能确认没有影响，且同类问题重复出现。
- **主题扩展**：深色、高对比或按页面切换主题进入范围，单层 `:root` 令牌和全局选择器难以支撑。
- **新交互类型**：图表、看板、拖拽排序、复杂树、虚拟表格等页面明显增加，手写布局和交互状态成本超过引入组件的成本。
- **协作可读性**：新增页面或 AI 生成页面时无法快速判断应复用哪个类，重复类名和新硬编码值持续增加。
- **组件行为缺口**：弹窗焦点、键盘操作、表格排序／选择等行为反复自建，缺陷率上升。

命中后默认按以下顺序评估，不直接全站换栈：

- **组件行为和无障碍是主要痛点**：优先 headless 组件库加现有令牌，CSS 写法不变。
- **样式编写效率和一致性是主要痛点**：试点 Tailwind CSS 或 UnoCSS，只在新页面或单个页面族使用，保留令牌和现有视觉。
- **需要现成后台组件且接受整体视觉改版**：再比较 Element Plus、PrimeVue、Naive UI 等完整组件库；这类方案要整体评估，不在局部页面混用。
- **只是类名冲突**：先评估 CSS Modules 或 `<style scoped>`，这是不增加运行时依赖的低成本方案。

任何试点都要写明范围、页面、依赖、构建变化、回退方式和验收证据；试点通过后修订本 ADR 或新增 ADR，再扩大范围。

## 后果与回退

- **收益**：样式集中、依赖少、构建链短；令牌和全局类可被所有 Vue 页面复用；人工和 AI 都容易按现有类名补页面。
- **代价**：全局类名没有作用域，页面增长后冲突和误覆盖风险上升；组件行为、可访问性和响应式细节需要自己维护；样式回归主要靠截图和人工走查，自动化覆盖弱；原生 `/` 与 Vue 应用各有一份令牌，取值不完全一致，迁移期存在视觉漂移。
- **回退**：如果后续引入 CSS 框架，保留 `:root` 令牌和现有视觉基线，按页面增量迁移；删除框架依赖和构建插件即可回到全局 CSS，不需要改 API、路由或组件数据流。回退条件与新方案一起写入修订后的 ADR。
