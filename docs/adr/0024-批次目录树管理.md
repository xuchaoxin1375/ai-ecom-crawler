## 状态与适用范围

**Provisional**（2026-11-27）。本 ADR 决定批次列表采用虚拟分组目录树、批次不嵌套、任务不跨批次移动，并用解散分组和归档代替物理删除。P1 已在独立 worktree 实现并通过后端 420 项、前端 170 项测试及 1280／390 走查，待项目方验收；设计细节、交互和验收见[批次目录树管理设计](../48-批次目录树管理设计.md)。

本 ADR 不改变任务状态机、计数口径、worker 调度、采集规则、交付快照和导出格式，也不实现物理删除、回收站、多父级标签或任务手工新建。

## 背景

批次列表目前是平面表格，靠状态、国家、分类、关键词和归档筛选找回批次。随着批次和任务增多，这种组织方式缺少稳定的项目层级：`category` 只能表达一个自由文本维度，无法表达“欧洲 / 英国 / 2026-11”这类路径；归档批次也没有固定的“已归档”入口。

直观想法是把批次做成目录、任务做成文件，并允许增删改查。但批次不是普通文件夹：

- 批次状态由站点和任务派生，批次嵌套会引入递归汇总、递归导出和递归归档。
- 任务通过 `batch_id`、`batch_sites.task_id`、`delivery_task_id` 和批次、站点、交付、质量反馈绑定，跨批次移动会破坏归属和导出。
- 批次和任务已经有关联结果、规则版本和构建记录，物理删除会留下孤儿数据。
- 任务由批次启动生成，不是用户手工创建的文件；给任务加“新建／改名／移动”会与运行时语义冲突。

因此需要把“目录树归类”和“对象归属”分开：目录只决定展示位置，批次和任务保持原有稳定关系。

## 决策

### 虚拟分组目录树

新增 `batch_folders` 表，分组可以嵌套；`batches` 增加可空的 `folder_id`。左侧树展示分组和批次，右侧内容区展示批次表或任务表。

- 分组是用户创建的归类目录，可包含子分组和批次。
- 批次是项目目录，只能属于一个分组，不包含子批次。
- 任务留在批次内容区，不进入左侧树，避免一个批次几十个站点、每个站点多次任务把树撑爆。
- “全部批次”“未分组”“已归档”是智能节点，不是真实存储行。

### 单父级与四层上限

首版保持单父级，不上多标签或硬链接。分组最多四层，同级分组名称唯一。单父级让移动、解散、计数和删除语义可预测；多维度整理后续用标签和保存视图补足。

### 任务不跨批次移动

任务仍属于原批次和站点。目录树只提供任务查看、暂停、继续、取消和归档；重新采集沿用批次复跑、试采转正式或站点构建流程。

### 解散分组与归档代替物理删除

- 删除分组等于“解散”：子分组和批次上移到上一级，不删除任何批次。
- 批次和任务继续使用现有归档／恢复语义，归档批次进入“已归档”节点。
- 物理删除不在首版；如后续需要，单独设计回收站、导出备份、终态限制和二次确认。

### 分类保留为标签

`batches.category` 继续作为扁平标签和筛选项，不自动转成目录。可提供一次性的“按分类生成分组”预览操作，保留分类值，不静默解释历史自由文本。

### 树接口轻量聚合

`GET /api/batch-tree` 只返回分组、批次名称、分组归属、更新时间和运行信号，不逐批次调用现有 `batch_payload`。树上的状态点只表示运行中、失败和待接入，完整批次状态仍由批次表和详情提供，避免第二套状态口径。

## 契约变化

- 新增 `batch_folders` 表、`batches.folder_id` 和对应索引；迁移为增量，现有批次落在“未分组”。
- 新增 `GET /api/batch-tree`、`POST/PATCH/DELETE /api/batch-folders...`、`PATCH /api/batches/{batch_id}`、`POST /api/batches/move` 和按 `folder_id` 筛选批次。
- `PATCH /api/batches/{batch_id}` 只开放名称、分类、备注和 `folder_id`；不改国家、市场、语言。
- 前端批次页增加目录树、批次内容区和任务内容区；保留现有批次表、筛选、批量操作和详情路由。
- OpenAPI 快照、前端 API 类型、文档索引和交接页同步更新。

## 备选方案

- **批次嵌套批次**：复用 `batches` 表增加 `parent_batch_id`，最贴近“批次即目录”的字面理解。但批次同时承担项目和分组语义，递归状态、计数、导出和归档都会变复杂，父批次自己的站点和子批次如何汇总也没有清晰答案。
- **通用树节点表**：用 `node_type` 表示分组、批次、任务，所有对象都作为树节点。灵活，但需要复制身份、同步引用和处理孤儿节点；首版收益不足以抵消复杂度。
- **任务自由移动或多父级标签**：允许任务挂到任意分组，看起来最像文件系统。但任务已有批次归属和交付链，移动会改变导出和计数；多父级还会让“删除分组”和“任务在哪里”变得含糊。
- **树中直接展开全部任务**：字面上最像文件树，但一个批次可能有几十个站点和多次执行，树会迅速失控。采用左树右内容区，任务仍然可点、可控、可导出。
- **物理删除 + 回收站**：更符合文件管理器直觉，但需要备份、依赖检查、保留期和权限设计，不适合与首版目录归类一起做。

## 后果与验证

- 用户可以稳定地把批次按项目、地区、客户或月份归类，同时保留平面表格的筛选和批量操作。
- 批次和任务的归属、状态、计数和导出不变；目录移动不会影响运行中的任务。
- 代价是目录树和内容区需要两套选中状态、URL 状态和返回恢复逻辑；树接口需要新的轻量聚合查询。
- 验收覆盖分组 CRUD、防环、限深、重名、解散上移、批次移动、归档恢复、批量移动回滚、只读、旧账本迁移、1280／768／390 布局和 8765 真实入口。
- 真实多用户权限、十万级批次、真实触屏拖拽和读屏全流程不在本轮验证范围。

## 复审条件

出现以下情况时重新评估本决策：

- 用户需要同一批次同时出现在多个目录，且标签／保存视图不能解决。
- 单父级四层上限成为主要阻碍，且有足够样本证明需要更深或网格结构。
- 批次需要真正包含子批次，且递归汇总、导出和归档语义能够被明确验证。
- 物理删除成为合规或容量硬需求，需要单独的回收站和审计设计。
