## 状态与适用范围

**Proposed**（2026-11-28）。本架构决策记录(Architecture Decision Record, ADR)决定保留候选规则激活门禁，并增加“全局默认 + 站点覆盖”的激活策略，让用户选择新规则在验证通过后是否需要人工确认。它修订[规则修复与异常工作流](../34-规则修复与异常工作流.md)第六节中“低风险修复可以评估自动激活，但默认不这样做”的表述：默认仍不自动激活修复，但新增显式配置入口；验证证据、激活事务、审计和回滚都不削弱。

本 ADR 不改变规则版本账本、任务绑定、复跑和结果采用语义，也不做多用户审批、规则编辑器或全量有效性隔离。设计细节见[规则版本激活门禁与可配置自动激活设计](../57-规则版本激活门禁与可配置自动激活设计.md)。

“是否启用规则版本激活”在本 ADR 中解释为“是否要求人工确认新规则生效”，不是删除规则版本或候选机制。任何自动路径都必须先生成候选并通过主机验证。

## 背景

当前实现有两条路径：

- 初始构建 `mode=build` 在主机验证通过后自动激活，审计记为 `actor=build`。
- 定向修复 `mode=repair` 默认只产生候选，等待人工激活；`ECOM_RULE_ACTIVATION_MODE=legacy` 可改回自动。

这套默认在早期是合理的：验证是抽样，坏规则会消耗采集预算、污染结果和导出；候选、验证证据和回滚让问题可追溯。但随着模型和系统改进，一次性写出的规则成功率提高，强制每次修复都人工确认开始产生不必要的摩擦。用户希望保留门禁的价值，同时能按站点和场景配置是否自动。

如果直接取消门禁，模型产出的规则会直接成为生产规则，失败只能事后回滚。当前还没有默认导出白名单和全量有效性隔离，直接取消的风险偏高。因此需要的是**可配置的确认策略**，而不是删除版本与证据。

## 决策

- **保留版本和证据**：候选版本、验证证据、激活审计、任务版本绑定和一键回滚全部保留；自动激活只改变“谁切换站点指针”。
- **四档策略**：`manual`、`auto_initial`（默认）、`auto_low_risk`、`auto_all`。`auto_initial` 保持当前“首次接入自动、修复人工”；`auto_all` 等价于关闭人工确认，仅显式开启，不作为默认。
- **首次接入判定保守化**：只有站点没有生效指针、没有历史运行、没有已交付结果时才算首次接入；已有规则的重写按修复处理，默认转人工。
- **全局默认加站点覆盖**：全局值存 `app_settings.rule_activation_policy`，站点可在同一 JSON 中覆盖；策略变更写审计事件。
- **构建入队快照**：本次实际策略、来源、风险、结果和阻断原因写入构建记录；后续设置变化不影响排队中和运行中的构建。
- **自动激活硬条件**：验证 `PASSED`、证据哈希一致、候选冒烟和回归满足要求、关联反馈检查通过、没有其他未纳入的开放反馈、站点空闲、无激活冲突，事务成功才切换指针。任一条件不满足就保留候选，转人工，不静默重试。
- **低风险由主机判定**：只有描述提取／清洗等白名单变更可以进入 `auto_low_risk`；发现、范围、市场、币种、价格、身份、图片、抓取引擎和 schema 变更均为高风险；无法归类按未知处理，转人工。
- **自动激活不自动复跑**：复跑涉及采集预算和范围选择，仍由用户发起；自动激活也不自动采用结果或关闭反馈。
- **审计可解释**：`rule_activations.actor` 使用 `local-user`、`build`、`auto-policy`、`legacy-build`；`reason` 记录策略、来源、风险和构建 ID。
- **环境变量保留为应急开关**：`ECOM_RULE_ACTIVATION_MODE=manual|legacy` 仍可强制全部人工或恢复旧自动行为；设置页显示覆盖并只读。页面配置不能绕过进程级覆盖。
- **一次构建只能收紧**：构建启动提供“本次先不自动使用新规则”，只能把自动改为人工，不能在系统或站点为人工时把本次改为自动。

## 备选与取舍

| 方案 | 结果 | 未采用原因 |
| --- | --- | --- |
| 完全取消人工激活 | 操作最少 | 规则直接进入生产，失败只能事后回滚；当前验证覆盖和结果隔离不足 |
| 保持强制人工、不提供配置 | 最安全、实现最小 | 不满足“模型改进后降低摩擦”的需求；所有修复都被同一门禁阻塞 |
| 全局单一开关 | 实现简单 | 无法区分首次接入、修复和低风险变更；要么过严，要么过松 |
| 每站点固定策略 | 边界清楚 | 不能表达“站点默认人工、低风险自动”；配置面也并不更小 |
| 每次构建弹窗选择 | 灵活 | 把风险判断推给用户每次操作，容易形成机械点击；策略不可审计 |
| 只按构建类型固定 | 与当前行为一致 | 不能配置，也不支持低风险自动 |
| 自动激活并自动复跑 | 一步完成 | 复跑消耗预算，范围可能需要选择；结果采用仍需人工判断 |
| 关闭版本账本 | 概念最少 | 失去候选、证据、审计和回滚，无法解释旧结果 |
| 全局默认 + 站点覆盖 | 默认安全、可按站点放宽 | 需要策略快照、审计和风险分类；采用 |

## 后果

- 默认行为在首次接入和修复上保持连续：首次接入自动、修复人工；已有生效规则的重写从一律自动改为默认人工，这是有意的收紧。现有站点不需要数据迁移，但需要知道重写路径的行为变化。
- 用户可以在受控站点选择更低摩擦的策略；`auto_low_risk` 依赖主机风险分类器，分类器必须保守并可解释。
- 设置、构建快照、审计和前端表达增加一层复杂度；需要新增测试覆盖策略优先级、快照隔离、阻断和事务失败。
- `auto_all` 会放大坏规则的影响，必须二次确认并持续提示；默认永远不是 `auto_all`，环境变量 `legacy` 只作应急。
- 自动激活后仍可能出现整站退化；回滚率和复跑后重开反馈率要进入观察，不能把“自动激活成功”当成“规则正确”。
- 策略变更不需要数据库大迁移；回滚到旧行为只需把全局或站点设为 `manual`，或设置环境变量 `manual`。已入队构建按快照执行，不会被追溯修改。
- 当前文档中的“自动激活未实现”仍然成立；本 ADR 只确认设计，代码、设置页和前端入口在后续阶段实现。

## 实施与验证

> 实现状态（2026-11-28）：仅完成设计文档和本 ADR，未改代码。后续按设计文档的分阶段计划实施，当前不声称已支持自动激活配置。

建议顺序：

- P1：后端策略存储、构建快照、`manual`／`auto_initial`、环境覆盖、审计和测试；默认行为不变。
- P2：设置页、站点覆盖、构建启动收紧选项、构建详情与任务反馈文案、“使用新规则并复跑”。
- P3：低风险分类器、`auto_low_risk`、自动激活指标。
- P4：评估 `auto_all` 是否开放界面入口；默认仍不是 `auto_all`。

验证至少覆盖：

- 默认策略下首次接入自动、修复人工；`manual` 下两者都人工。
- 站点覆盖、环境覆盖和“本次收紧”的优先级正确。
- 策略变更不影响已排队和运行中的构建。
- 站点忙、未纳入的开放反馈、验证不足、回归退化、哈希不一致和激活冲突都不会自动切换指针。
- 自动激活写 `auto-policy` 审计；事务失败时指针不变；回滚仍可用。
- 自动激活不自动创建复跑、不自动采用结果、不自动关闭反馈。
- 设置页和构建详情的业务文案、390 视口、只读与环境覆盖状态通过走查。
