## 状态与适用范围

**Proposed**。方向已由项目方确认（2026-11-20）；任务管理 API、Web 界面和资源配额尚未实现和验证，验证后转 Accepted。

本文补 [任务运行时与并行模型](0003-任务运行时与并行模型.md) 未覆盖的三件事：一个任务对应多少站点、并发和浏览器实例怎么分配、产品界面取什么形态。任务状态、计数和操作语义仍以[任务状态与计数契约](../09-任务状态与计数契约.md)为准；界面行为以[界面与任务管理](../06-界面与任务管理.md)为准；运行细节以[采集规则与任务运行时](../19-采集规则与任务运行时.md)为准。本文不改变 ADR 0003 的任务账本、工作项和控制边界。

## 背景与约束

- 用户对批量采集管理的预期接近下载管理器（IDM／Motrix／AriaNg）：多个任务相互独立，可暂停、恢复、取消、删除和回收。
- 但采集任务与文件下载不同：总量通常未知、单页耗时差异大、站点有礼貌约束、浏览器实例是稀缺资源。
- 用户确认：产品界面为本地 Web UI；单机单用户；通常一个采集任务对应一个网站；任务内并发可控制；进度以计数为主，不要求进度条。
- v1 仍是 CLI＋SQLite＋线程池，Web UI 在任务层稳定后包装同一服务，不另写一套业务逻辑（ADR 0001／0003）。

## 决策

### 任务粒度

- 默认一个采集任务 = 一个站点 × 一个规则版本 × 一个市场；范围、预算和输出属于任务参数，不拆成第二个任务。
- 同一站点的多个任务只在明确场景允许：复采、规则版本切换、不同市场／语言、不同采集深度。它们各自独立计数，不合并成“站点总数”。
- 站点分组、批次视图只做展示和筛选，不改变任务边界，也不产生跨任务计数。
- 任务创建入口是规则包和站点，不是任意 URL 输入框；URL 清单是 discovery 任务的产物，不是任务身份。

### 并发与资源配额

- 并发分三个层次，不能用一个“连接数”概括：
  - 全局任务槽位 `max_concurrent_tasks`（默认 2）；
  - 每任务工作项并发：`concurrency.navigation` 和 `concurrency.product` 分开；
  - 每任务浏览器实例上限，以及全局浏览器实例上限。
- 站点级限速按可注册域（eTLD+1）聚合，跨任务共享；robots 的 `Crawl-delay` 是下限，任务只能更慢，不能更快。
- 浏览器实例和内存是准入条件：配额不足时任务保持 `QUEUED` 并给出原因，不先启动再争抢。
- 同一站点的两个任务并行时，共享站点限速器和会话资源；任一任务暂停或取消，不影响另一个任务的状态和计数。
- 采集任务不假设独占域名；资源配额和站点限速是调度层事实，不写入任务计数。

### Web 界面形态

- 产品形态是本地 Web UI：单机单用户，默认只绑定回环地址，浏览器访问；v1 不做桌面壳（Tauri／Electron），后续需要托盘或系统通知时再加壳，引擎和 API 不变。
- 采用引擎／界面分离：任务服务提供 REST 控制和 SSE 事件，CLI 与 Web 共用同一任务层；前端不直接读数据库、不启动采集进程。
- 控制接口返回“已受理”，最终状态以任务账本为准；断线重连先拉快照，再订阅增量。
- 前端框架不限；交互参考下载管理器的任务列表、队列和详情，但不照搬其“文件大小／百分比”语义。
- Web UI 的交付晚于 CLI 和任务账本；界面缺失不改变任务契约（ADR 0003 的分期不变）。

### 进度与计数表达

- v1 以计数为主：已发现网址、已处理、有效、排除、失败、待处理、在途；任务列表和详情都能直接看到这些数。
- 只有 `coverage.status = KNOWN` 或存在明确预算上限时，才显示比例；其余情况显示阶段和计数增长，不编造覆盖率、百分比或剩余时间。
- 进度条、瞬时速率、ETA、图表属于进阶项，不作为 v1 验收条件。
- discovery 任务显示 URL 计数，product 任务显示商品计数；两者不互相折算（`09`、`19`）。

### 操作语义补充

- 暂停默认是“停止派发，在途结清”（`PAUSING` → `PAUSED`）；强制中止在途属于进阶项，必须单独标识，并说明未完成工作会回到待处理。
- 恢复前校验规则版本、市场、环境和配额兼容性；不兼容时提示新建任务，不静默换规则或市场。
- 归档只改变可见性；永久移除删除任务记录、结果和产物，不删除共享规则包、配置或其他任务数据。
- 删除产物可能遇到文件占用（浏览器 profile、日志、SQLite 临时文件），采用异步回收并报告残留，不用同步删除假装成功。

## 后果

- 任务账本需要 `site_key`、`domain_key`、配额字段和浏览器实例计数；这些是调度字段，不进入业务 CSV。
- 任务 API 至少覆盖创建、启动、暂停、恢复、取消、归档、移除、计数查询和导出；UI 只消费 API。
- 需要测试：同站两任务共享限速、配额不足排队、暂停在途结清、恢复兼容性、删除残留报告。
- 站点分组和批次视图可以后置，不影响一站一任务的契约。
- 未来上多机或队列时，站点限速和全局槽位需要外置；任务粒度不变。

## 为什么不选其他方案

- **桌面壳（Tauri／Electron）作为 v1**：能提供托盘和通知，但增加打包、签名和自动更新成本；本地 Web 已能满足单机单用户。
- **一个任务覆盖多个站点**：会让失败、预算和计数混在一起，暂停和删除的边界也说不清；批量需求用批次视图表达。
- **默认允许同站多任务并行且各限各的**：实际请求速率会翻倍，违反站点礼貌和 A20；必须共享站点级限速。
- **直接采用 Crawlee／Scrapy 的任务队列当任务管理**：它们的队列是单次 crawl 的请求前沿，不是任务账本；状态、计数和验收语义仍要自有（见 `13` 的任务管理层分析）。
- **以进度条和 ETA 作为 v1 验收**：总量未知时无法诚实计算，容易把部分结果包装成全量。

## 跟进

- 在 `19` 的任务字段和并行模型中补 `site_key`、`domain_key`、`max_browser_instances` 和准入原因。
- Web UI 先做任务列表、详情、控制和计数展示；批次、通知、图表后置。
- 用 R16 切片补同站两任务、配额排队和暂停／恢复测试。
- 实现后在 `06` 的界面验收和 `05` 的 A20 记录证据，再转 Accepted。
