## 状态与适用范围

**Proposed**。本文给出 v1 的技术基线提议，用于让 D01 有明确的验证对象；未在真实站点和实际环境验证前，不得写成已实现、已定型或已通过。

本文只决定技术方向和接口边界，不改写业务口径。字段、价格、描述、任务状态、计数和验收场景仍以 `01`～`09` 为准；方案包结构以 [采集方案与兼容契约](../08-采集方案与兼容契约.md) 为准。本文的取舍背景见 [需求对照与取舍](../11-需求对照与取舍.md)。

## 背景与约束

- 单用户、单执行机、多网站并发，兼容 Windows、Linux 和 WSL2。
- 运行语言取 Python 3.11+；Scrapling 0.5.x 要求 Python 3.10+，项目以更高版本为准。
- AI 在构建期理解站点并生成方案；正式执行不逐页调用 LLM。
- 站点差异留在方案包，不接一个网站就修改公共引擎。
- 需要覆盖公开结构化数据、普通 HTML、站点地图、分类分页、动态渲染和有限的反爬／挑战。
- 优先免费、开源、可自托管，不依赖按页或按任务计费的强制配额。
- 方案包要能导出、导入、版本检查和复跑，不依赖私有会话、Cookie 或本机绝对路径。
- 代码主要由 AI 生成，接口应简单、可观察、可回滚，错误要能定位到网址、字段和阶段。

## 决策摘要

| 领域 | v1 基线 | 备选或退出条件 |
| --- | --- | --- |
| 运行形态 | 本地单用户服务；FastAPI 提供 API；每个任务由受管子进程执行 | 多用户、多机时改为 PostgreSQL＋独立队列 |
| 采集执行 | Scrapling 0.5.x 的 Spider 和 Fetcher 作为主执行能力，固定 minor 版本 | D01 证明 0.x 稳定性或状态映射不足时，换 Crawlee 1.x；静态批量可评估 Scrapy 2.20 |
| 规则形式 | YAML manifest 加 JSON Schema；声明式规则、Python adapter 或混合 | 纯 YAML 只用于简单站点；纯 Python 只用于复杂交互 |
| 方案入口 | 子进程读取任务上下文 JSON，按 NDJSON 输出事件和结果 | 同进程 import；独立 HTTP 服务 |
| 数据存储 | SQLite WAL 加 SQLAlchemy／SQLModel；结果另存 CSV／JSON 文件 | PostgreSQL；对象存储 |
| 任务调度 | 单服务加资源受限的 worker 子进程；v1 不引入 Celery、Temporal 或 Redis | 多机、多用户或长任务队列化时再引入 |
| 界面 | 前后端分离；本地 HTTP API；CLI 与 Web 共用同一服务 | 桌面壳；现成面板；远程部署 |
| Agent | harness 中立；参考默认 OpenCode 加 DeepSeek V4.1 Flash；构建期外部进程 | pi-agent、codex 或其他能产出方案包的宿主 |
| 反爬 | Scrapling 的静态、动态、挑战能力，配合方法 04 的有界比较和资源回收 | 合法代理、会话复用或人工协助；不绕过登录和付费 |
| 资源回收 | 自建浏览器、进程和临时目录登记；取消后拒绝迟到结果 | 容器隔离、受管浏览器服务 |

## 候选框架对比

以下只核对公开文档和包元数据，**没有做本机安装、性能测试或成功率测试**。版本和状态以 2026-11-18 的公开页面为准，采用前必须按实际锁定版本复核。

| 候选 | 公开能力 | 主要风险 | 在本项目中的角色 |
| --- | --- | --- | --- |
| Scrapling 0.5.1 | HTTP、动态和 stealth 抓取；自适应选择器；Spider 并发、暂停恢复、AutoThrottle、代理轮换、重试、流式输出；Sitemap／Shopify 模板；MCP 和 Agent Skill；BSD-3-Clause | 0.x Beta；生态和 API 仍在演进；浏览器资源和任务状态需要外层映射 | **v1 主执行能力** |
| Crawlee for Python 1.11.2 | 请求队列、浏览器池、并发、重试、代理和会话、持久存储、Sitemap 加载；Apache-2.0；Production/Stable | 不以内置自适应选择器和挑战处理为核心；与 Scrapling 同时使用会增加浏览器生命周期复杂度 | 稳定性优先时的备选骨架 |
| Scrapy 2.20 | 成熟的静态抓取、选择器、AutoThrottle、任务暂停恢复、Feed 导出；生态大 | 动态渲染和挑战处理要额外集成；Twisted 与项目异步栈的耦合成本较高；AI 生成站点逻辑的样板较多 | 静态大批量站点的备选 |
| Crawl4AI 0.9.5 | LLM 友好的 Markdown、结构化抽取、浏览器控制、反爬与会话、无 LLM 的 CSS／XPath 抽取；Apache-2.0 | 定位偏 LLM 和内容抽取；运行时容易引入不必要的模型调用；浏览器较重 | 可选的正文抽取后备，不作为核心 |
| 薄 Python 编排器 | 完全可控，接口简单，容易把站点方案做成子进程 | 队列、重试、检查点和资源回收要自己维护 | Scrapling 状态映射不足时的后备 |

## 为什么以 Scrapling 为主

Scrapling 同时覆盖了本项目最难的几件事：静态请求、动态渲染、挑战页面、会话复用、自适应选择器，以及带暂停恢复的 Spider。它的 Agent Skill 和 MCP 也能降低构建期 AI 的学习成本。对“AI 生成站点方案、框架离线执行”的目标，它比单纯静态框架更贴近完整链路。

它的代价同样明确：

- 0.x Beta 不适合直接假设长期 API 稳定，必须锁定 minor 版本并在方案包里记录版本范围。
- Spider 的 `crawldir` 只解决抓取层恢复，不等于 `09` 的任务状态和计数；外层服务仍要对账。
- 公开资料里的挑战处理是能力声明，不是本项目实测通过率；按 `03` 和方法 04 做有界验证，不承诺所有 Cloudflare 站点可采。

Crawlee 的队列和浏览器池更成熟，但它不提供同等的自适应选择器和挑战能力，最终仍要接入 Scrapling 或其他抓取层。为避免两套浏览器生命周期互相打架，v1 先用 Scrapling 一条链路；只有 D01 证明它的队列、恢复或资源回收不够稳定时，才把编排层换成 Crawlee，方案包契约不变。

Scrapy 仍是静态大批量站点的可靠备选。Crawl4AI 的 LLM 抽取能力适合作为正文后备，但不进入默认运行时，避免普通批次变成逐页模型调用。

## 方案包与执行契约

方案包继续遵循 `08` 的 manifest 字段，并补足以下运行约定：

- `manifest.yaml` 是入口，使用 JSON Schema 校验；`schema_version` 与 `plan_version` 分开。
- `kind` 取 `declarative`、`program` 或 `hybrid`。简单商品页用声明式规则；需要点击、滚动、登录态以外的公开交互或复杂分支时用 Python adapter；两者可以混合。
- `program`／`hybrid` 的 `runtime.entrypoint` 指向方案包内的相对路径。执行端以子进程启动，不把方案代码 import 进主服务。
- 子进程输入一份任务上下文 JSON，至少包含 `task_id`、`plan_id`、`plan_version`、范围、市场、语言、资源上限、检查点目录和输出目录。
- 子进程向标准输出写 NDJSON 事件，至少区分 `state`、`counts`、`product`、`excluded`、`failed`、`log` 和 `checkpoint`；标准错误保留诊断日志。
- 执行端按 `(task_id, product_key)` 或 `(task_id, normalized_source_url, plan_version)` 幂等接纳结果；取消后到达的事件按 `09` 拒绝，不进入有效集。
- 方案包不携带密钥、Cookie、浏览器 profile、任务进度或审批状态；密钥由目标环境注入。

这套契约解决 `08` 当前的待确认项中的序列化、程序入口和证据边界；`verified` 的最小证据集仍可在 D09 收紧。

## 数据与状态

- SQLite 使用 WAL 模式，保存任务、任务事件、已发现网址、商品候选、已接纳结果、检查点和构建会话。单用户 v1 不需要额外的数据库服务。
- Scrapling 的 `crawldir` 只作为执行层恢复缓存；`09` 的任务状态、计数和有效结果以服务端接纳的事实为准。重启时先对账，不把缓存里的“看起来完成”直接当成功。
- 正式运行默认不保存整页 HTML／JSON；开发样本和诊断材料按任务有界保留。结果导出使用 `02` 的 CSV 和 JSON 结构。
- 如果后续出现多 worker 写竞争、多用户或远程执行，再迁移 PostgreSQL；迁移前不引入第二套状态真源。

## 界面与 API

- 前端只通过本地 HTTP API 访问任务、商品、方案和构建会话，不直接读数据库或启动采集进程。
- CLI 与 Web 共用同一服务层；命令行不是第二套业务逻辑。
- API 至少覆盖任务创建、启动、暂停、恢复、取消、归档、移除，商品和网址查看，结果导出，方案导入导出，以及构建会话的查看、暂停、停止／取消和移除。
- 构建会话的暂停只在工具调用边界生效：当前调用结束后不再派发下一步；强制停止要取消当前调用并回收子进程。不能承诺暂停模型内部推理。
- 默认只绑定本机回环地址；前端不显示密钥、Cookie 或完整认证头。HTML 预览按不可信内容处理。

## Agent 与模型

- 构建 Agent 是执行端之外的进程或会话，通过方案包交付，不进入正式运行依赖。
- 参考默认是 OpenCode 加 DeepSeek V4.1 Flash 免费版，仅用于降低首次试验成本；pi-agent、codex 或其他兼容宿主可以替换。
- 记录实际模型、供应商、调用次数、耗时和费用；不保存模型私有推理，只保留公开活动、工具结果、试跑证据和下一步。
- 普通批次不调用 LLM；Crawl4AI 的 LLM 抽取也不作为默认路径。

## D01 验证计划

D01 至少用四类路径验证本 ADR：

- 普通 HTML 加站点地图。
- 分类／分页或公开目录。
- 动态渲染或公开 JSON 接口。
- 有限反爬、429 或挑战页面。

记录构建耗时、实际模型调用、执行耗时、有效商品数、部分描述比例、人工介入、方案导入结果，以及浏览器和进程的启动／回收数量。通过线仍按 `04` 和 `05` 的核心闭环执行：A08、A09 先过，再补 A10、A13、A16。

出现以下情况时按退出条件处理，不硬扛：

- Scrapling 的 Spider 状态无法可靠映射到 `09` 的计数和取消语义，改用 Crawlee 或薄编排器。
- Scrapling 0.x 的升级破坏方案 API，锁定版本并把适配层独立出来，必要时换执行层。
- SQLite 出现持续写竞争或任务量超出单机预期，迁移 PostgreSQL。
- 挑战处理需要绕过登录、付费或明确访问控制，停止并记录边界，不把它包装成技术问题。

## 风险与未决

- Scrapling 仍标记为 Beta；本 ADR 不把它的挑战处理写成保证，也不把公开文档当成实测。
- Scrapling 的 `crawldir` 与服务端检查点是两套状态；实现时必须明确谁是真源，避免重复计数。
- 子进程加 NDJSON 增加一层协议，但换来语言和运行环境解耦；需要为事件格式和退出码写验证。
- SQLite 适合单用户 v1，不适合多 worker 长期并发写；迁移路径要预留。
- Crawlee、Scrapy、Crawl4AI 的版本和许可证按上游实际锁定版本核对；本文只记录公开状态。
- 代理、会话复用和挑战处理受站点条款、robots 和当地法律约束；技术可用不等于获得授权。
