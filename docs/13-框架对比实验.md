## 用途与边界

本文登记一个**预注册的框架对比实验**，用来回答：在相同模型、相同站点、相同数据标准和相同预算下，AI 使用不同爬虫框架构建可复跑采集方案的效率差异。

它是 [技术栈与运行形态 ADR](adr/0001-技术栈与运行形态.md) 的 D01 输入，不是框架功能大全，也不是生产实现。实验结果只证明本次站点、版本和环境下的表现，不能直接外推成“某框架永久最好”。

## 要回答的问题

- 同一 AI、同一批站点、同一数据标准下，哪个框架更快产出**首个有效商品结果**和**可复跑方案**？
- AI 的 API 错误、文档查询、工具调用失败和人工介入，在各框架下分别占多少时间？
- 增加一个字段或修复一个选择器，需要多久？哪套方案更容易维护？
- 运行时质量、资源回收、取消和方案导入复用，是否达到现有契约？
- 最终应选择单一框架、混合方案，还是保留多个备选？

## 假设

以下是待验证假设，不是结论：

- **H1**：带 Agent Skill 和 MCP 的 Scrapling 能缩短首个有效结果时间，尤其是在动态和挑战页面。
- **H2**：Crawlee 的请求队列和浏览器池能降低并发、重试和资源回收类错误。
- **H3**：Scrapy 在静态站点和站点地图批量发现上更省资源，但动态和挑战页面需要更多集成工作。
- **H4**：AI 对框架的熟悉度、文档质量和 API 稳定性，会解释构建时间差异的显著部分，不能只归因于框架能力。

## 站点与范围

D01 从[验收基准站点](12-验收基准站点.md)中选 **3～4 个站**，覆盖以下路径类型：

| 路径类型 | 选择要求 | 记录 |
| --- | --- | --- |
| 静态 HTML＋站点地图 | 公开可访问，sitemap 有商品页 | 入口、sitemap、商品页上限 |
| 分类／分页／公开目录 | 至少有下一页或分类分支 | 入口、分页深度、去重规则 |
| 动态渲染或公开 JSON | 需要浏览器或可复现公开接口 | 实际就绪条件、接口证据 |
| 限流或挑战 | 有 429、Cloudflare 或类似边界 | 请求上限、退避和停止条件 |

默认每个站最多取 **30 个商品页或 10 分钟**，先到为准；D01 可以调整，但所有参与框架必须使用同一上限。只取公开商品，不登录、不下单、不绕过付费或访问控制；请求速率和 robots／ToS 边界在实验记录中写清。

本轮站点、范围上限、通过线和签字人填写在 [D01验证模板](14-D01验证模板.md)；本文只取其中参与框架对比的部分，不另存一份站点表。

## 实验设计

### 控制变量

| 变量 | 控制方式 |
| --- | --- |
| 模型 | 同一供应商、同一模型、同一版本和同一参数 |
| Agent harness | 同一宿主和同一工具权限；不因框架切换宿主 |
| 提示词与任务规格 | 同一份任务说明、数据标准、输出格式和验收规则 |
| 站点与范围 | 同一批站点、同一入口、同一商品页上限和时间上限 |
| 网络与出口 | 同一网络、代理和地区；记录实际出口标识 |
| 资源预算 | 同一并发、请求上限、超时和重试上限 |
| 会话 | 每个框架使用全新会话，不复用其他框架的代码或上下文 |
| 顺序 | 随机化框架执行顺序，降低学习效应 |
| 评审 | 同一评审人，按日志和结果表打分，不凭记忆 |
| 数据标准 | 统一使用 `02`，不得为某个框架降低字段要求 |

### 分支与目录

推荐使用 **worktree＋独立目录**，分支只做一次性隔离：

- 基线分支：`exp/framework-compare`，只放共享的任务规格、站点名单、评分表和报告模板。
- 每个框架一个 worktree 或目录，例如 `experiments/framework-compare/scrapling/`、`crawlee/`、`scrapy/`；各自建虚拟环境和锁文件。
- 如果必须用分支，命名 `exp/fc-<framework>`，从同一基线提交分出；不要长期保留多套半成品，也不要把所有实现都合进 `main`。
- 实验结束只合入结果报告和胜出的脚手架；失败实现归档或删除，保留日志和证据。
- 共享目录只放规格和评分，不放某个框架的实现代码，避免跨框架“抄作业”。

### 单次运行流程

1. 预检同一模型、宿主、网络、浏览器和依赖可用性。
2. 在默认 **90 分钟**内完成方案构建和首次有界试跑。
3. 记录首个有效商品结果时间、首次完整方案时间和所有错误。
4. 完成一次修复任务：增加一个字段或修复一个选择器，默认 **30 分钟**内完成并复跑。
5. 在干净环境导入方案，执行一次小批量复跑。
6. 用日志和结果表填写指标，不在运行后改评分规则。

如果某个框架在时间盒内没有产出有效结果，记录失败和阻塞点，停止该框架的后续阶段；不要给它额外时间后与其他框架比较。

### 停止条件

- 无法在时间盒内产出符合 `02` 的有效商品。
- 必须降低字段要求、改样本或绕过质量门禁才能继续。
- 需要登录、付费或明确访问控制。
- 出现无法回收的浏览器、进程或临时目录泄漏。
- 依赖或运行环境无法在同一条件下稳定复现。

## 指标

| 维度 | 指标 | 记录方式 |
| --- | --- | --- |
| 构建效率 | 首个有效商品时间、首次完整方案时间 | 从任务开始到实际结果的时间戳 |
| AI 交互 | 模型调用次数、token、工具错误、API 错误、文档查询、人工介入、修订次数 | 从会话日志和工具日志计数 |
| 修复效率 | 增加字段或修复选择器的时间、复跑是否通过 | 修复任务开始到通过的时间 |
| 运行时质量 | 基础字段核对、有效商品、排除、失败、部分描述、请求数、墙钟时间 | 按 `09` 的计数口径 |
| 采集深度 | 各页面层级请求数、每有效商品请求数、每有效商品下载字节、发现阶段每100请求新增唯一实体URL、入口贡献/重叠、重复率、部分枚举、浅层字段命中率、详情补全比例 | 运行日志和结果表；按页面层级分别统计 |
| 资源 | 浏览器和进程启动数、峰值内存、回收结果、残留 | 运行记录和进程快照 |
| 复用 | 干净环境导入结果、依赖检查、首次复跑是否成功 | 按 `08` 和 `10` 的兼容检查 |
| 成本 | 模型、代理、浏览器和人工时间 | 实际账单或估算，注明口径 |

不以代码行数、文件数或“看起来简单”代替效率。主观感受可以记录，但必须和日志、时间和结果分开。

## 评分与判定

先过硬门禁，再比较效率：

- 必须满足 `02` 的字段、价格、描述和导出要求。
- 普通批次不得逐页调用 LLM。
- 方案包满足 `08` 的 manifest、版本、兼容和证据要求。
- 任务状态、计数、取消和迟到结果满足 `09`。
- 浏览器、进程和临时目录有实际回收。
- 不越过登录、付费和访问控制边界。

硬门禁通过后，按首个有效结果时间、修复时间、有效商品数、资源回收和复用结果做对比。**不做一个加权总分**，避免用速度掩盖失败项；报告分别列构建、运行、修复、资源和限制，再给出 v1 推荐。

如果结果支持混合方案，例如“Scrapy 做静态发现，Scrapling 做动态商品页”，应作为新的 ADR 提案，不直接写进公共引擎。

### 第 1、2 轮（javaestate.com、skatepro.es）

三臂的分臂报告和评审记录在 `experiments/framework-compare/results/`。第 1 轮按旧 22 列合同、第 2 轮起按 9 列合同记录；两轮都有 `PARTIAL`／`BUDGET_EXHAUSTED` 样本，只证明该站该次预算下的表现，不构成全站覆盖。

### 2026-11-19 补充探针（sixmoondesigns.com、campsaver.com）

| 站点 | 路径 | 结果 | 结论 |
| --- | --- | --- | --- |
| `sixmoondesigns.com` | Shopify 公开 `/products.json` | Scrapling HTTP 200、Scrapy HTTP 200、Crawlee `HttpCrawler` 403 → `PlaywrightCrawler` 200；三臂各取前 30/112 个商品，24 个描述完整、6 个未提供 | 公开 JSON 路径可行；Crawlee 的 HTTP 客户端需换浏览器客户端，Scrapling／Scrapy 的 HTTP 客户端更轻 |
| `campsaver.com` | 挑战页 | curl 307 → `forbidden.html`；Scrapling `StealthyFetcher`（含 `real_chrome`）与 Playwright 均未取得商品 | PerimeterX 风格，不是 Cloudflare；三臂共同边界（默认无头栈），不能作为框架区分证据；有头复核见 `experiments/framework-compare/probes/README.md`，站点并非不可采 |

探针固定条件、原始 JSON／CSV 和复跑命令见 `experiments/framework-compare/probes/README.md`。探针会话使用 ERNIE 5.5 Flash，不是本实验固定的 DeepSeek V4.1 Flash，因此构建耗时不能与第 1、2 轮合并排名；探针也不是正式 D01 轮次，不据此改写 S4／S6 的站点状态。

本轮尚未形成 v1 推荐；正式 D01 需在同一模型、同一站点清单和同一预算下补跑动态／挑战路径，再更新 ADR。

## 任务管理层：框架覆盖边界（2026-11-20 公开资料分析）

本节回答“Scrapling、Crawlee 这类框架是否覆盖批量站点任务管理”，是公开资料核对，**不是 D01 实验的一部分，也没有本机实测**。它只比较任务管理边界，不比较抓取能力、吞吐或成功率。

### 请求队列不是任务队列

- Crawlee 的 `RequestQueue` 管理一次 crawl 的 URL 前沿：去重、重试、持久化和并发；它没有定时、任务目录、跨任务预算、优先级和人工审批。
- Scrapling 的 Spider 覆盖并发、按域并发上限、`download_delay`、robots、检查点和暂停／恢复；同样以“一次 crawl”为生命周期。
- Scrapy 通过 `JOBDIR` 恢复、AutoThrottle 和 RetryMiddleware 覆盖单次运行；Scrapyd 提供 job 级部署、schedule 和 cancel，没有 pause／resume API；Gerapy／ScrapydWeb 补面板、定时和多节点，但仍以 job 为单位。
- Apify 把 Crawlee 的编排、存储、代理和运行历史做成平台能力；这是商业平台，不是 Crawlee 库本身。

### 能力对照

| 能力 | Crawlee | Scrapling | Scrapy |
| --- | --- | --- | --- |
| URL 去重与重试 | 有 | 有 | 有 |
| 并发自适应 | AutoscaledPool | 按域并发、AutoThrottle | AutoThrottle |
| 暂停／恢复 | 队列不 purge 可续跑 | checkpoint＋pause／resume | `JOBDIR` |
| 会话／代理 | SessionPool、ProxyConfiguration | 代理轮换、会话复用 | 需扩展 |
| 持久化 | 文件、SQL、Redis 存储客户端 | 本地文件 | 自建／scrapy-redis |
| 跨任务调度 | 无（Apify 平台有） | 无 | 无（Scrapyd 生态有） |
| 任务账本／预算 | 无 | 无 | 无 |

### 可选方案

| 路线 | 代表 | 得到什么 | 代价 |
| --- | --- | --- | --- |
| 平台托管 | Apify、Zyte 等 | 调度、运行历史、存储、代理 | 计费；任务语义仍要包一层 |
| 框架生态 | Scrapy＋Scrapyd＋Gerapy／ScrapydWeb | 部署、版本、job API、多机面板 | 只服务 Scrapy；维护活跃度按采用时点复核 |
| 通用调度 | Celery／RQ／Arq、Temporal、Airflow／Dagster、K8s Job＋KEDA | 成熟的任务状态机、重试、定时 | 要写爬虫 worker 适配层；单机 v1 过重 |
| 自建账本 | SQLite／PostgreSQL＋调度循环 | 与 `09` 契约完全对齐 | 并发、恢复、多机要自己补 |

### 对本项目的判断

- 框架只作为执行引擎，任务账本、状态机、预算和验收仍由本项目持有（ADR 0003）。
- v1 不引入 Celery、Temporal 或外部队列；出现多机、定时、任务量上量或需要人工审批时再升级。
- 引擎适配层按“取一个工作项→返回结果或失败分类”设计，Scrapling 是第一个实现，Crawlee 可作为第二个实现。

来源（2026-11-20 核对，未做本机实测）：[Crawlee storages](https://crawlee.dev/python/docs/guides/storages)、[Crawlee storage clients](https://crawlee.dev/python/docs/guides/storage-clients)、[Scrapling Spider advanced](https://scrapling.readthedocs.io/en/v0.4.1/spiders/advanced.html)、[Scrapy jobs](https://docs.scrapy.org/en/latest/topics/jobs.html)。

## 风险与限制

- **熟悉度混杂**：AI 对不同框架的先天熟悉度是实验对象，不是噪音；用 API 错误和文档查询记录它，但不额外给某个框架提示。
- **站点差异**：站点结构、出口和限流会变化；同一站点尽量在同一时间窗内完成。
- **学习效应**：同一模型可能记住前一轮代码；使用全新会话、随机顺序和独立目录，禁止跨框架复制实现。
- **样本太小**：3～4 个站只能证明路径类型，不代表全站覆盖率或长期稳定性。
- **版本漂移**：框架升级会改变结果；固定版本并在报告中记录。
- **分支漂移**：多分支容易长期分叉；用 worktree，实验结束及时归档。
- **合规边界**：小请求量、公开页面、遵守 robots／ToS；实验不等于访问授权。

## 非目标

- 不是所有爬虫框架的完整基准。
- 不是生产应用实现，不替代 D03／D04 的核心闭环。
- 不是全站覆盖率或字段准确率证明。
- 不是“某框架永久最好”的结论。
- 不因为实验方便而降低 `02`、`08`、`09` 的要求。
