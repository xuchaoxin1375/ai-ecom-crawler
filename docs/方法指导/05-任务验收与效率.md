## 真实入口与轻量观察

1. 确定任务目标和数量限制；默认目标全量，试跑／灰度另标，不擅自降为几条样本。
2. 确认真实执行服务、环境和必要工具就绪，复用正常服务，不为每次验收再启动一套。
3. 使用一次真实创建入口和幂等身份提交，保存任务标识；已提交继续观察原任务，不因等待超时重复创建。
4. 后续读取轻量状态，仅阶段变化、错误或约定心跳时汇报，不循环拉取整页HTML、完整商品或全部日志。
5. 必要时复用一次认证会话检查界面，数据计数仍以后台接纳事实为依据。

观察的时间边界不等于后台采集截止。停止轮询时说明任务是否仍在运行；后台正常推进后转回其他开发工作，不一直等待全量结束。

## 效率和责任归属

记录提交、分析、发现、获取、提取、验证及交付耗时；实际模型调用、尝试、后备和人工等待分别列明。没有Agent调用、Agent使用后备、环境输入错误和网站访问受阻不能合并成“模型失败”。

实际吞吐使用明确时间窗的请求／有效商品计数，注明站点规模、执行环境、网络出口和方案版本；配置的每秒请求数不等于真实产出速度。重试不重复计入商品。

## 采集深度与效率预算

效率不是“跑得快”，而是用可接受的请求、时间和存储拿到业务需要的字段。**先定页面层级，再定请求预算**，不要先写选择器再发现总量太大。

### 先算再跑

- 按页面层级列出候选：入口／目录、列表／型号／系列、详情、搜索或公开接口。
- 抽样 10–30 个页面，记录平均响应大小、延迟、字段命中率和重复率。
- 估算总请求 ≈ 各层候选数之和；下载量 ≈ 总请求 × 平均页面大小；墙钟时间 ≈ 总请求 × 平均延迟 ÷ 有效并发。
- 有效并发受站点限流、解析、重试和资源约束，不等于配置的 RPS；估算要给重试和失败留余量。
- 预算超出时，按顺序调整：减少深层请求、收窄范围、降低字段目标，最后才考虑提高并发。

### 浅层优先

- 列表／型号页已能提供名称、编号、价格、状态、缩略图时，先以该层为主数据源。
- 详情页只补列表层没有的正文、规格、兼容关系或结构化报价；同一字段不在多层重复抓取。
- 无法确认详情页的增量价值时，先抽 20–50 个详情页对比字段完整度，再决定是否全量下钻；抽样按来源、品牌和层级分层随机，不取发现顺序前 N 个。
- 详情页确有独有字段但预算不足时，保留核心字段并明确标记未补字段，不能伪称完整。

默认验收先核对基础字段：身份与来源 URL、名称、价格与币种、状态、主图，以及描述是否存在。完整正文与规格、兼容关系、选项变体、文档和全量覆盖属于进阶项；任务未要求时不作为通过条件，也不默认全量下钻。

基础字段按门店／市场核对：按重量或长度计价的商品保留计价单位与单位价（如 `per lb`），不把单位价当包装价；多门店站点的价格和可售状态只在对应门店成立，不能把一家门店的状态当全站。公开接口返回的状态要先确认是门店级、市场级还是默认店级。

变体商品：基础价取公开最低变体价，商品可售＝任一公开变体可售；一个变体缺货不等于整品停售；缺 SKU 用商品 ID／handle＋选项值，不把每个变体当独立商品。父级 JSON-LD availability 不能替代变体级库存。

多市场：同一商品按目标市场分别记录价格／币种；不跨市场取最低价或仅按汇率换算；价格单位先确认（Shopify `.js` 常为分，WooCommerce `display_price` 常为十进制）。

多卖家 marketplace：商品页与 item 页是商品／offer 两级；先定输出单位。商品页 AggregateOffer 的 low／high／count 是当前 offer 汇总，历史 price guide 不是当前价；item 页 seller／condition／price／shipping 逐 offer 记录，运费注明目的地；推荐卡价格不能当主价。

源码与可见状态不一致，或关键字段疑似由 JS 渲染时，可用浏览器截图核对首屏或目标区块；截图只证明可见状态，不替代批量字段提取、计数和导出核对。

SPA 首屏为空壳时，先从内联配置找 API host／path，并用一次浏览器 XHR 记录请求头；补头后用 HTTP 重放。JSON `403 AccessDenied` 先按缺客户端头排查，仍被拒按权限边界停止；不逐页渲染已验证有公开 JSON 的商品。公开 JSON 目录读分页元数据（skip／take、page／limit、total），空页或 skip ≥ total 停止；sitemap 与 API total 差异留档，不强行对齐。多门店跨店合并先用 UPC／EAN／GTIN／MPN 验证，URL UUID／slug／catalogue ID 可能只是门店级。

有挑战求解引擎（如 Scrapling）时优先使用；普通 Playwright 只作对照或后备，不先用它证明挑战不可过。同站连续取数先预热一个浏览器会话，复用 clearance 和 profile，不逐页重开浏览器。代理只改变出口，不替代挑战求解；是否切换要与直连做同条件对照。裸 403 无挑战特征且同站另一出口 200 时，按出口地区／IP 拒绝处理，换出口复测，不升浏览器。

### 深度选项

| 深度 | 适用 | 得到的字段 | 代价 |
| --- | --- | --- | --- |
| 只取列表／型号层 | 价格、库存、目录、型号关系 | 核心字段，可能缺正文／兼容关系 | 请求最少 |
| 列表层＋按需详情 | 核心字段＋部分正文／规格 | 取决于缺失字段比例 | 请求量可控 |
| 全量详情 | 字段要求完整，详情页确有独有字段 | 最全 | 请求、存储和时间成倍增加 |

### 效率指标

报告至少记录每有效商品请求数、每有效商品下载字节、各页面层级请求占比、浅层字段命中率、重试率、墙钟时间和资源回收。发现阶段另记每 100 个请求新增的唯一实体 URL、各入口贡献和重叠；这些指标用于调整 frontier，不是最终商品计数。配置并发、请求数或“看起来快”不能替代这些事实。

覆盖率不是默认交付指标。结构清晰、入口和身份稳定时，只报已走路径、剩余入口和停止原因；有可靠分母且需要全站审计时才计算覆盖比例。

## 结束与报告

任务失败先归因，不为单站随意加公共引擎特例。已发现成员处理完与全站覆盖分开；用户验收、自然结束、截断和失败分别保留。

报告至少包括范围、实际运行模式、各阶段时间、模型调用、确定性计数、有效／部分内容／失败情况、停止原因、未覆盖边界和下一步。界面截图只能证明可见交互，不证明数据库、导出和完整性正确。

这些经验来自任务验收Skill；原批次API、Temporal、旧执行档及固定轮询参数没有作为新团队要求带入。
