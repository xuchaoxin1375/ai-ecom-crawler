## 目的与边界

本文复盘[验收基准站点](../12-验收基准站点.md)中的代表性站点，把采集从“发现网址”推进到分诊、获取、提取、校验和效率停止。数字只证明当日样本；原名单优先，外部补充站只在覆盖缺口时使用，并记录来源与证据。

## 阶段默认

| 阶段 | 先做什么 | 证据 | 效率与停止 |
| --- | --- | --- | --- |
| 分诊 | 每个入口 1 个请求：状态、标题、robots／sitemap、平台与市场 | 403／406／429／挑战、最终 URL | 1 请求／入口；不先开浏览器；挑战页按项目预算追加有头／会话复核 |
| 发现 | sitemap／公开 API → HTML 索引／分类 → 分页 | 候选 URL、入口贡献、分母 | 唯一实体 URL／请求；无新身份／预算／部分枚举 |
| 获取 | 含基础字段的静态／JSON／列表 → 详情 → 浏览器 | 字段是否已在响应；请求头与会话 | 请求数／有效商品；404／410／空页／total |
| 提取 | 列表层基础字段优先；详情只补缺 | 字段来源、商品归属 | 字段命中率；模板差异 |
| 校验 | 10–30 个分层样本：基础字段／状态／描述 | 样本矩阵、冲突 | 有效率／部分率；质量阻塞 |
| 效率／停止 | 每有效商品请求数／字节、墙钟、并发 | 实测吞吐 | 到预算／访问边界 |
| 交付 | 证据、部分、复跑 | 来源／日期／出口／停止原因 | 不把样本写成全站 |

## 效率计算

- sixmoons：1 个 API 请求约 1.2MB／112 商品 ≈ 10.7KB／商品；商品页 0.84–1.3MB／页，112 页约 94–146MB；API 省约 80–120 倍字节。
- javaestate：707／250 = 3 页，约 2.7MB；3 个请求 vs 707 个详情页。
- fooddepot／afsupermarket：19,129／100 = 192 个列表请求；100 条约 246KB，合计约 47MB 基础字段；19,129 个详情页只用于描述，按缺失率决定是否下钻。
- skatepro：8,399 × 10s ≈ 23.3h；按 3,504 个商品计算约 9.7h；全量前先算墙钟，预算不够就收窄。
- partsfornissans：40–88s／页；100 页约 1.1–2.4h；会话复用和按需详情是主要优化。
- shopthebulkstore／tognar／repairtoolparts：静态请求秒级；无浏览器；只取主容器。

## 策略改进

- 首页 1 个请求可筛平台／访问／商品链接；平台标记和首页 JSON-LD 只作线索，商品页模板可能不同（tognar 首页无 Product JSON-LD、商品页有 2 个；PrestaShop 常无 JSON-LD）。
- API／列表一次取多条，详情只补缺；先算每有效商品的请求数和字节数。
- sitemap 数量不等于商品数；分类页或公开 API 可能是主入口，记录入口贡献。
- 分页先读 total；空页或 `skip >= total` 停止；sitemap 与 API total 差异留档，不强行对齐。
- 变体商品：单个零价变体不等于整品零价；取有价变体的最低正价，零价变体单独记录；全部变体零价／无价才按 quote-only 或无效处理。
- 变体也可能是独立商品 URL（颜色／尺寸各一页）；单页没有 selects 不等于无变体，按商品名、属性、父子关系和业务键归并。PrestaShop 独立颜色页即使都自指 canonical，也只是一个型号的多个颜色；用 SKU／GTIN 做变体键，不能把 canonical 或标题当唯一身份。
- 价格按 locale 解析（`39,00 € TTC`、`206,90 €`）；优先 `product:price:amount`／`itemprop="price"`，否则锚定主价格容器，区分现价与划线价。
- BigCommerce 的 Product JSON-LD 不只一种形状：价格可能在 `offers.price`，也可能在 `offers.priceSpecification.price`；描述可能在 JSON-LD 缺失、只在商品页 DOM。结构化数据缺字段先查主题容器，不据此判原站未提供。
- 无 JSON-LD 的站仍可能有 Product 微数据（`[itemtype*="Product"]`、`[itemprop="price"]`／`sku`／`availability`）；先查微数据，再退回 DOM，不因缺少 JSON-LD 判无结构化字段。
- 自定义站的 `web_page`／`ware` 混合路由常见：sitemap 可能混编辑页和政策页，不能按路径形态或条数判商品；分类页 `product_box` 往往比 sitemap 更接近商品入口。
- 同型号的多个面料／颜色可能是独立商品页（如 24 个 `product_box`），不是单页选项；按标题／SKU 归并为变体家族，`?fabric=` 一类是筛选参数，不是新商品。跨变体共享的模板描述可记完整，但要注明非变体特有。
- 内部 `mpn`／ERP 标识不等于公开 URL；不要用 mpn 拼 `/ware/<id>`，公开身份用页面 canonical 或 microdata `url`。
- Shopify 可能输出多个 Product JSON-LD：主题块（带 `@id`／productID）与评价／富摘要 app 块（如 `y-rich-snippet-script`）冲突时以主题块 + `products.json` 变体状态为准；app 块的 availability 可能过期。
- Shopify 多变体商品的 AggregateOffer 可能只有 low／high／offerCount、没有 availability；按 variants 的 `available` 或 select option 的 `disabled` 判变体状态，不只看父级 JSON-LD。
- Shopify 描述完整文本用 `span.description` 或 JSON-LD description；宽泛 `.rte` 可能只取到 intro。主价用 meta／主题 JSON-LD／`price-list`，页面其他 € 文本（免邮门槛）不是商品价。
- 缺货商品源码可能仍有价格和加购表单；状态用 JSON-LD `availability`、内嵌商品 JSON 的 `instock` 与 `og:availability` 交叉核对，不按加购按钮单独判定。
- ObjectPath／JS 店面的商品链接可能返回首页；记录导航／会话边界，不据此判无商品，也不反复重试同一条链接。
- 客户端和出口差异先比较一个变量；429 退避或换出口，403 先分挑战、地区／IP 与权限。
- 挑战站会话复用、按需页面、有限尝试；不逐页重开浏览器，不反复重试同一条失败路线。
- 有 `Crawl-delay` 时先算墙钟；预算不够就收窄范围或降低字段目标，不先提高并发。
- 校验用 10–30 个分层样本，覆盖入口、列表、详情、变体、缺货、描述缺失；失败和未测项保留。

结论：

- 技能阶段表的主干（分诊→发现→获取→提取→校验→效率／交付）得到多路径支持，可以作为 D01 的默认流程。
- 但阶段表不等于站点通过线：当前证据多为模板探针，不能写成 10–30 样本验收、全站覆盖或长期稳定。
- 最需要补的不是更多站点，而是同一代表站的正式 D01 轮次：同模型、同预算、方案包、独立执行、复跑和失败样本。
- 框架对比的 ERNIE 探针只作方向证据；正式结论必须与 DeepSeek 轮次同模型补跑。

D01 前必须补：

- 选 3–4 个代表站，覆盖静态／API、分类分页、动态／挑战、变体。
- 每站按 10–30 个分层样本或明确预算执行；记录有效、排除、失败、部分、待处理。
- 保存 manifest 方案包，并用独立命令复跑，记录运行期 LLM 调用应为 0。
- 挑战站按有头／会话复用执行，记录请求数、出口、客户端和停止原因。
- 统一效率表：每有效商品请求数／字节、墙钟、并发、重试。
- 结果回写 [验收基准站点](../12-验收基准站点.md)、`13`、ADR 和 `10` 的状态看板。
