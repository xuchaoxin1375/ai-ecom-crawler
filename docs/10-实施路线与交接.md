## 关键路径

```text
A1 → D01 → D02 → D03 → D04 → { D05, D06, D07 } → D08 → D09
```

- A2 在 D08 前完成即可，不必挡住 D01～D04；界面原型可提前，接线要等 D04／D07。
- A3 在对外分发前完成，可与 D01／D02 并行。
- ADR 是 D01 的输入，不是已定结论；D01 验证不通过时按 ADR 的退出条件换执行层或存储，不硬扛。
- D05、D06、D07 在 D04 之后可以并行，不要串成一条长链。
- D09 最后做，但目标站点名单和通过线必须在 D01 就定，不能等实站评估时再补。

## 排序理由

- **先闭环，后广度**：01／04 已明确，第一阶段先证明“AI 建方案 → 框架独立执行 → 输出合格结果 → 同方案复跑”，不要让大面板、万能动作语言或跨站覆盖抢在前面。
- **D02 在 D03 前**：数据合同、9列业务CSV和任务报告异常索引是方案构建的输入；先定字段再建方案，返工最少。
- **D01 先定站点和通过线**：12 的完整名单是基准集，05 的首批历史候选只是线索；等 D09 才定目标，验收一定会漂。
- **D05～D07 是质量补强**：兼容、跨路径、可靠性在核心闭环之后并行补，不要为了“看起来完整”拖长 D03／D04。
- **每个环节都要有证据门**：08 的方案包、09 的状态与计数、A01～A18 的场景；模型自报、文件存在、截图好看都不算通过。

## 新 Agent 会话如何继续

读取顺序：

- [开工前检查清单](21-开工前检查清单.md)：正式开工前的立项、契约、证据和交付门禁；不替代 15 的当前状态。
- `docs/README.md` → 01～09 → 10／11／12 → 14／术语表（按需）→ 13（按需）→ ADR。
- 业务口径以 01～09 为准；11 记录与原需求的差异，12 是基准站点，13 是框架对比实验，ADR 是技术提议。
- ADR 未验证前不要写成已实现；D01 验证后更新状态和限制。

开始前检查：

```powershell
git status --short
git log -1 --oneline
git remote -v
```

不要做：

- 不要把已删除的 `resilient-browser-fetch` 旧 zip 重新加回；需要代码时按当前上游版本核对。
- 不要把方法 04 当成某个固定上游版本的完整 API 文档。
- 不要在未确认的情况下改动 01～09 的业务规则；先说明影响和替代方案。
- 不要把 12 的基准集当成逐站通过线，也不要把未测站写成通过。
- 不要把 ADR 的 Proposed 当成已定技术方案；D01 验证前只能作为提议引用。
- 不要把框架对比做成不同站点、不同预算或不同提示词的比较；按 13 控制变量。
- 不要先做 D08 大面板或万能平台，再补 D03／D04 核心闭环。

验证与提交：

```powershell
python scripts/export_docs.py
python scripts/export_docs.py --check dist/ai-ecom-crawler-docs.zip
python scripts/check_docs_links.py
uv run ruff check scripts
```

- 内链由 `scripts/check_docs_links.py` 检查相对链接和包内路径，不校验锚点与外部网址；导出脚本的 `--check` 只校验文件哈希。
- Python 环境用 uv 管理（`pyproject.toml` 与 `uv.lock`）；uv 未在 PATH 时用 `python -m uv run ruff check scripts`。只有文档脚本需要环境，采集运行时依赖不属于本仓库。
- 提交信息沿用 `docs: ...` 风格；Windows 下含中文的提交信息先写 UTF-8 文件，再用 `git commit -F`。

## 风险与注意

- 范围膨胀：先做通用平台、全站覆盖或高级分析，会拖住 D03／D04；按 01 的优先级收敛。
- 目标漂移：D01 不固定站点和通过线，D09 容易用“做过的站”替代“承诺的站”。
