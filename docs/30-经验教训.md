## 用途与边界

本页记录 2026-11-21 D08 设计讨论、仓库整理和浏览器 adapter 验证中形成的可复用教训，供本项目后续开发和类似项目参考。它不替代业务规则、ADR 或 skill 正文；具体操作规范分别落在 `swe-gov`、`frontend-design`、`repo-gov` 和 `resilient-browser-fetch`。

## API 契约清楚不等于前端设计清楚

「契约冻结后前后端可以并行」默认假设有独立的前后端实现者和评审上下文。单人或单个 coding agent 串行开发时，物理上仍是一前一后；如果先把后端和数据契约定完，再让 Agent 按 API 字段生成页面，很容易出现：

- 页面按字段直排，用户任务和信息层级没有单独设计；
- 空态、失败态、部分结果、控制已受理和禁用状态在实现时才临时决定；
- 设计和实现互相追着改，评审只能用已经写好的页面，形成循环论证；
- 负责人没有前端设计背景时，Agent 把“你想怎么布局”原样抛回，推进停滞。

本项目的具体表现：D08 页面先于独立设计稿实现，1280 复核最初用的是已实现页面；质量异常曾直接显示整段 JSON；后来补了初步设计稿和用户视角的状态整理。

可复用做法：

- 把前端设计当成独立工件：目标用户、主流程、页面清单、信息层级、状态矩阵、主规格线框、关键取舍；
- Agent 先出 2–3 个可预览方向、推荐稿和取舍，负责人确认业务目标和选择，不要求负责人先画线框或写 CSS；
- 设计决定先于页面扩散；实现可以按用户任务的纵向切片串行推进，但不要用 API schema 直接生成页面结构；每个切片以整体设计基线为准，只补本切片的增量；
- 纯 CRUD、内部工具且交互显然时可以简化设计稿；面向运营／分析人员的控制台、长任务、多状态页面不适用豁免；
- 小团队或单人亦可只维护一份轻量设计稿，不强行拆前后端两套流程。

## 任务控制台不等于产品界面

D08 的页面先按任务／规则包 API 做出来，能创建、控制、计数和导出；但用户拿一批站点来时，第一步就卡在“选哪个规则包”。它证明的是任务控制链，不是用户工作流。

定位判断：

- **作为内部技术预览：有价值。** 它验证了任务状态、控制语义、计数、质量异常、导出和账本恢复，也可以作为未来“批次 → 站点 → 任务”的任务详情基础。
- **作为业务产品界面：不合格。** 第一对象是规则包而不是站点／批次；任务列表是扁平的；没有站点导入、接入状态、批量操作和批次交付。
- **不能靠在任务列表上加一个批次筛选来修补。** 对象模型不对，加筛选仍然是任务中心界面；需要把批次和站点变成用户对象，规则包降为内部资产。
- **可复用判断：** 先问“用户从什么对象开始”，再定页面；内部资产不要进主流程；能用一个具体用户任务走不通时，不要用“页面已经能点”证明设计成立。

## 全局原型不是页面拼图

- 新建或整体改版界面，先做应用外壳、导航、入口与出口、跨页面主流程、全局状态和对象关系，再拆单页。孤立页面做得再完整，也回答不了“用户从哪来、下一步去哪、失败后怎么回来”。
- 原型可以使用 mock 数据并独立于后端；后端尚未实现不构成跳过设计门的理由。实现页面、接口联调页和单页 demo 都不能替代全局原型评审。
- 评审按代表任务走完整流程，例如“导入一批站点 → 判断可采性 → 启动 → 处理失败 → 导出 → 找回”；只看首屏或几张截图，容易把局部整洁误当成整体可用。
- 设计交付至少包含：全局壳与导航、页面清单、跨页主流程、对象模型、关键状态、线框或可浏览原型、明确不做的范围。缺跨页流程的页面清单不算全局设计。

## 运行期数据库不应随仓库分发

任务账本、SQLite 数据库及其 WAL／SHM 是本机运行状态，通常具有以下问题：

- 二进制、易冲突，无法可靠 review 或合并；
- 会随着运行增长，包含任务历史、临时状态甚至用户数据；
- 不同机器、不同任务的数据库不能互相替代，提交后容易让后来者误以为它是可复用的 fixture；
- 证据价值不如任务结果、CSV、事件摘要和可重跑命令稳定。

本项目已将 `tasks.db` 等运行期账本移出版本控制，加入忽略规则；需要长期保留的证据使用 `task-result.json`、`products.csv`、`records.jsonl`、事件摘要和复跑步骤。

例外：小型、合成或脱敏、测试确实需要的 fixture 数据库可以保留，但必须写明用途、生成方式和例外规则；不因为扩展名一律忽略合法 fixture。

## 实验证据入库要分级

`experiments/` 是验收证据和原型，不是生产代码；文档里的结论依赖它才能核对和复跑，所以整体应随仓库走，但不能把所有文件都当成同一种材料。

- **入库**：规则包、方案、脚本、测试和 fixtures，`task-result.json`、`products.csv`、`records.jsonl`、对照结果、事件摘要，以及写清目的、命令和边界的 README。它们体积小、可 diff，能说明“哪个提交、什么条件下得到这个结论”。
- **有条件入库**：截图和录屏。它们证明界面在某个时点的状态，事后无法原样重拍；只保留每个验收节点的定稿，同一节点内的迭代图替换而不是累积，单张控制在 500 KB 内，超出时先压缩或裁切。真实任务截图只留必要的一组，不加入登录态或客户数据。
- **不入库**：脚本生成的导出包、运行期数据库、`.venv`／`node_modules`、浏览器 profile、整页 archive 和日志。导出包和源数据并排会静默过期，review 时看不出差异；保留生成脚本、命令和一份规范位置的样本即可。

判断顺序是先看用途，再看体积和扩展名：同是二进制，验收截图和虚拟环境不是一类；同是生成物，可复跑的证据摘要和导出包也不是一类。历史提交不会因为后来移出文件而缩小，规则要在证据量还小时定下来。

本项目现状：`experiments/build-agent/*/task-export.zip` 由 `run_real_build.py` 生成，内容来自同目录的任务结果和 CSV，已移出版本控制并加入忽略规则。当前 `.git` 约 22 MB，不引入 LFS；当已跟踪二进制超过约 50 MB、单文件接近平台限制，或证据开始包含私有数据时，再评估独立证据仓库或对象存储。

## 工作区跟踪检查

- 提交前看 `git status --short`、`git diff --cached --stat` 和 `git ls-files -c -i --exclude-standard`，区分“本次改动”“用户手工改动”和“生成物”。
- 已追踪但应忽略的文件用 `git rm --cached -- <file>` 移出版本控制，保留本地内容；不要 `git rm` 删除用户文件。
- 发现运行时数据库、日志、缓存、浏览器 profile 或可再生成产物被追踪时，先核对用途再处理，不无差别清理。
- 运行期数据被忽略后，工作区仍可能保留文件；这是有意为之，不代表提交遗漏。

## 跨平台行尾与生成文件

2026-11-22 在 Windows 上多次看到 `git add` 提示 `CRLF will be replaced by LF`，`git ls-files --eol` 显示 `i/lf w/crlf`。这不是提交失败，也不是 `core.autocrlf` 单独造成的：仓库 `.gitattributes` 已把索引归一为 LF，但工作区文件被编辑器或脚本重新保存成了 CRLF；归一化时共有 417 个已跟踪文本文件处于该状态。

可复用做法：

- 先看实际状态，不按警告方向猜：`git ls-files --eol -- <path>`、`git check-attr text eol -- <path>`、`git config --show-origin --get core.autocrlf`。
- 仓库级规则优先于个人配置：`.gitattributes` 写 `* text=auto eol=lf`，`.sh`／`.bash` 明确 LF，`.bat`／`.cmd` 明确 CRLF；`.editorconfig` 固定编辑器默认 LF，并给 `.bat`／`.cmd` 留 CRLF 例外。
- 索引已归一但工作区仍是 CRLF 时，警告会持续到工作区重写；不要用 `core.autocrlf` 或 `core.safecrlf=false` 静音。归一化工作区后，用 `git add --renormalize .` 刷新索引状态。
- 只有 `.sh`／`.bash` 和 `.bat`／`.cmd` 是运行硬要求；其他文本保持 LF 主要是为了 diff、证据和跨平台复现，不是为了“能跑”。
- 不建议默认加自动修复的 pre-commit 钩子：它会改工作区但未必重新暂存，部分暂存时容易混入未确认改动。需要时用 check-only 脚本或 CI；`--fix` 由用户显式执行并 review。
- 多平台开发的风险来自平台、编辑器或 Git 默认值不同，不是 Git 传输或地理距离；新机器克隆后抽查 `w/crlf`，编辑器支持 EditorConfig 时保持 LF。

本项目现状：`.editorconfig` 和 `.gitattributes` 已补；工作区 `w/crlf=0`；历史 warning 不影响已提交内容。

## 挑战壳的 HTTP 状态不等于渲染后的状态

浏览器抓取时，`page.goto()` 返回的是首个主文档响应。站点可能在 403／429／503 壳里运行自己的 JS，随后重新导航到真实页面；此时首个响应仍是 503，但最终 DOM 已经可用。

可复用做法：

- 用明确的 DOM 就绪信号（真实标题、商品容器、`wait_selector`）判断内容是否渲染，不要只看首个 HTTP 状态。
- 渲染完成后读取 navigation timing 的 `responseStatus`，它通常反映最终文档；拿不到时回退到首个响应并在结果里标注。
- 不要因为“最终 200”就忽略挑战：如果没有就绪信号、标题仍是挑战文案或正文仍是壳，应按 `ACCESS_DENIED` / 失败流记录。
- 这类等待只给站点自己的验证留时间，不做点击、过验证码或绕过登录／付费；headless 通过也不等于站点长期稳定。
- 证据里同时写首个状态、最终状态、等待方式、渲染耗时和停止原因，避免把“浏览器能打开”写成“站点可全量采集”。

本项目的 mercerine 证据：首个响应 503，渲染后 `responseStatus=200`，3／3 商品页有效；见 `experiments/d07/browser-mercerine/`。

## CSS 选择器解析通过不等于执行器能执行

`familidoo.fr` 的构建规则在面包屑字段使用了 `nav.breadcrumb_nav a:not(:first-of-type)`。`cssselect.parse()` 能解析它，但 `lxml.cssselect.CSSSelector()` 转 XPath 时失败：`ExpressionError: *:first-of-type is not implemented`。主机验证把 3 个商品页都记为 `plan_error`，最终只显示“0 有效、3 失败”，真实原因被计数和 `stop_reason` 盖住。

根因不是选择器语法本身，而是**校验使用了错误的执行语义**：解析器接受不等于目标执行器能执行。可复用做法：

- 规则进入联网验证前，用与运行时相同的选择器引擎（这里是 `lxml.cssselect`）编译所有 CSS 选择器；不要只做 YAML／正则自检。
- 静态预检要覆盖发现、提取、价格对和选项组等所有进入运行时的选择器；`wait_selector` 属于 Playwright 语义，不能混用 lxml 预检。
- 验证失败时把 `stop_detail` 和失败样例带回给构建 Agent，而不是只回“有效数为 0”；同一会话修复一轮后再预检和验证，避免重新做整站调研。
- 预检和修复轮次都要有上限，并把轮次、错误和是否解决写入构建 trace；否则“自动修复”会变成不可复盘的重试。

本项目的实现：`app/src/ecom_crawler/executor/preflight.py` 和 `BuildManager._start_repair`；测试见 `app/tests/test_preflight.py` 和 `app/tests/test_builds.py`。证据见 `experiments/build-agent/real-model-2026-11-23-familidoo-trace/`。
