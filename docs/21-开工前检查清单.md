## 用途与边界

本页把“可以开始实现”拆成可逐项核对的检查项，供项目方、技术负责人和承接方在正式开工前使用。它只汇总 [项目定位](00-项目定位与可行性.md)、[开发任务](04-开发任务与交付.md)、[实施路线](10-实施路线与交接.md)、[交接](15-交接.md)、[规则与运行时](19-采集规则与任务运行时.md)、[环境基线](20-构建环境与依赖基线.md) 和 [网址发现与分页策略](22-网址发现与分页策略.md) 已有的门禁，不新增业务口径；业务规则仍以 01～09 为准，当前状态仍以 [交接与继续](15-交接.md) 和 Git 为准。

只有存在可复核证据时才勾选；未勾选项写负责人、阻塞范围和截止条件。勾选不表示“讨论过”，也不把 Proposed 写成已实现。

## 业务与核心机制

核心功能开工前，在已有需求或设计页记录以下决策。局部修复只补受影响的约定。

| 要定清的事 | 可检查的结果 |
| --- | --- |
| 用户要完成的工作 | 用代表场景说明谁在何时发起、已有做法、预期结果、受阻后怎么继续。用用户可见的结果做验收。 |
| 本轮功能取舍 | 每项功能有明确的使用场景、用户决定或必要约束。按业务影响、实际使用机会、开发与维护成本决定保留、合并、删除或后置。 |
| 核心工作机制 | 写清关键对象、状态归属、触发、异步受理、结果生效和恢复。多角色、跨组件或复杂状态用 Mermaid 表达，配一条主路径及最重要的异常路径。 |
| 尚未解决的关键决定 | 开工前处理会改变工作流、数据归属、契约或验收的分歧。可利用现有资料和小样验证，仍需业务取舍时明确决策人及受影响范围。其余可逆假设注明复查条件。 |

当前批次工作流沿用[用户工作流](33-用户工作流与前端信息架构.md)，待施工范围和验收写回[批次改进计划](45-批次采集与交付改进计划.md)。

### 开写前必须确认

技术选型是开工前的硬门，不是实现中的可选项。前端、后端、数据存储、部署方式和构建工具等每个进入生产路径的层，都必须先有结论；没有结论时也必须给出基于现有信息的推荐、理由、风险和复审条件，不能留空后边写边选。

当前状态：批次工作台按 ADR 0009（Vue 3 + TypeScript + Vite，阶段 1 已实现并验收，v2 默认后降级）；任务页面按 ADR 0012 的 v2 React 栈，任务控制台并入见 ADR 0010（Accepted，验证 partial）；样式层见 ADR 0011（手写 CSS + 令牌，不引入 CSS 框架／UI 组件库，验证 partial）；前端见 ADR 0012（React + Tailwind v4 + 自有组件层，Provisional，唯一入口，根路径直出，旧 Vue 与 `/legacy` 已删除）；旧原生页面见 ADR 0008，已删除。系统 v2 的规则版本账本／反馈 API 见 `34`，仍为 Proposed；进入 `app/` 生产路径前需改为 Accepted 或登记 Provisional 例外。后端 ADR 0001～0003 已定，0004／0006／0007 为受限 Provisional；FastAPI 与替代 Web 框架的对比见 ADR 0001。
